# 임베딩 v1 확정 계획 — 후보 수집 → 일괄 판정 → 선택 → 검색 파이프라인 (2026-10-15, kse16 반영 2026-10-16)

회의·인수인계용 요약 문서. 규칙의 근거는 `docs/EVALUATION_POLICY.md`(평가·판정 공식 규칙), 서비스 적용 전체 그림은
`docs/SERVICE_READINESS.md`.

## 0. 한 장 요약

- **지금 단계는 "임베딩 단계(관련성 판단)" 평가다.** 검색·추천 시스템은 단계별로 개발·평가한 뒤 붙여서 전체를 검증하는 것이 업계 표준이다
  (후보 생성/순위 분리: Covington et al. RecSys 2016, 임베딩 상품 검색: Nigam et al. KDD 2019). 위치·거리 정렬은 뒤 단계의 일이다.
- **임베딩은 이번 일괄 판정 1회로 v1을 고정한다.** 현재 벤치마크는 천장 근처(판정 문서만 nDCG 0.95~0.96)이고, 남은 차이(0.01)는 val 124개로
  구분이 안 된다(필요 쿼리 약 515개). 더 튜닝해도 개선인지 잡음인지 판별할 수 없다.
- **임베딩 모델만 후보로 모은다**: kse16(Qwen3 0.6B 확정 run)과 팀원들이 학습한 bge-m3·Snowflake Arctic 최고 run → 한 번에 보충 판정 → val로 하나 선택 → test 1회.
- **하이브리드·reranker는 후보에서 뺀다.** 어떤 임베딩 위에든 얹는 검색 구성 요소라 임베딩 선택과 분리되고, 효과는 실제형 쿼리·위치가 붙은
  ④⑤ 단계에서 재야 의미가 있다. 지금까지의 측정(1절 아래 표)은 파이프라인 설계용 사전 탐색으로 남긴다.
- 그 다음 **검색 파이프라인(위치 필터·정렬, 하이브리드, reranker 여부, 벡터 DB/ANN 색인)을 구현**하고, 실제 쿼리+위치로 전체 성능을 잰다.
  부족하면 그때 실제 쿼리 기반 데이터로 재학습한다(현재 val에 맞추는 학습은 하지 않음).

- **nDCG@10(주 지표)·Precision@10**: 상위 10개가 맞는 업종인가. 둘이 거의 같이 움직인다.
- **MRR@100**: 첫 정답이 몇 위인가. 대부분 1위라 0.94~0.97로 거의 포화 — 모델 차이가 잘 안 보인다.
- **Recall@50/100, Bpref**: 정답 중 상위 50·100개 안에 든 비율. 정답이 100개보다 많은 쿼리가 65%라 Recall@100은 구조적으로
  최대 약 0.85(평균)까지만 가능하고, 실제 코퍼스의 정답(예: 치킨집 3,000여 개)은 더 많아 **낮게 나오는 게 정상**이다. 절대값보다 모델 간 차이로 본다.
- 모델 선택은 nDCG@10과 기준 대비 Δ·p(Δ ≥ 0.03, p < 0.05)로 한다(`docs/EVALUATION_POLICY.md` 4절).

- kse14 = `qwen3_embedding_0_6b_ft_kse14_20261014_0440`: LoRA rank 16, GIST loss, lr 1e-4, batch 32, **2 epoch**, 학습 쿼리 215개(6,650행),
  T4 fp16, 오타 증강 끔, hard negative 3. 모델은 `models/`(git 제외), 기록은 `results/finetune_runs/`.
- **kse16** = `qwen3_embedding_0_6b_ft_kse16_20261016_0012`: kse14와 같은 설정에서 **hard negative만 3 → 6**(학습 데이터 sha `ec3a9b61` 동일, T4 43분).
  kse14 대비 nDCG@10 +0.002(p=0.45, 같은 수준), MRR@100 +0.007(p=0.38), **Recall@100 +0.012(p=0.0001)**, bad@3 12 → 7(6개 해결·1개 악화,
  부호 검정 p≈0.13 — 방향은 맞지만 val 124개로는 확정 불가). 2026-10-16 Qwen3 0.6B 후보로 확정하고 기준선을 kse16으로 바꿈.
  kse16 + 하이브리드 행은 `eval_retrieval_stack.py`와 같은 RRF(k=60)·채점으로 계산(reranker 조합은 미측정).
- reranker 구성은 판정 안 된 문서를 위로 올려 공식 점수·bad@3이 낮게 나온다(Judged@10 0.82~0.93) → ⑤의 실제형 평가셋에서 판정과 함께 잰다.
- **하이브리드**: 키워드 검색(BM25)과 임베딩 검색의 순위를 합친다(RRF: 각 결과의 순위 역수를 더함). 상호명·정확한 단어는 BM25가, 뜻이 비슷한 표현은
  임베딩이 잡아서 서로 보완한다. **reranker**: 1차 검색 상위 수십 개를 쿼리와 가맹점 문장을 함께 읽는 더 무거운 모델(cross-encoder)로 다시 정렬한다.
  더 정확할 수 있지만 쿼리마다 수십 번 계산해서 지연·GPU 비용이 든다. 둘 다 "검색 → (결합) → 재정렬" 파이프라인의 부품이다.
- 같은 설정도 다시 돌리면 nDCG@10이 ±0.005 흔들린다(kse1·kse13·kse14).

### 1-1. 후보 3종 비교 — 일괄 판정 라운드 `final_v1_val` 결과 (2026-10-16)

**판정**: 세 후보의 val 상위 10개 중 미판정 220쌍을 A·B 독립 판정(일치 93%, 198행 자동 확정) → 22행 조정(전부 supplement_v2의 v1.2 선례와 같은 값으로
확정) → qrels_val +217행(판정 불가 3행 제외). 판정 전 공식 nDCG는 bge-m3 0.840(미판정 189쌍), Arctic 0.947이었다 — 판정 누락이 순위를 뒤집고 있었다.

**쌍별 비교** (paired permutation, nDCG@10, `results/model_comparison/final_v1_val/pairs.csv`)

| A vs B | Δ nDCG@10 [95% CI] | p | wins/ties/losses |
|---|---|---|---|
| Arctic lee vs kse16 | +0.008 [−0.005, 0.023] | 0.28 | 15/97/12 |
| bge-m3 mj vs kse16 | +0.007 [−0.008, 0.024] | 0.45 | 14/98/12 |
| Arctic lee vs bge-m3 mj | +0.001 [−0.010, 0.012] | 0.84 | 13/99/12 |
| Arctic **zero-shot** vs kse16 | −0.001 [−0.017, 0.016] | 0.91 | 14/93/17 |
| kse16 vs Qwen3 zero-shot | +0.034 [0.021, 0.048] | 0.0001 | 36/84/4 |
| bge-m3 mj vs bge-m3 zero-shot | +0.042 [0.024, 0.062] | 0.0001 | 40/78/6 |
| Arctic lee vs Arctic zero-shot | +0.009 [0.002, 0.017] | 0.016 | 16/102/6 |

**해석**
- **세 후보는 같은 수준이다**(5절 규칙: Δ ≥ 0.03·p < 0.05 아님). 5절 3번(서비스 지표)도 bad@3 6·7·8개, 1위 정답률 0.976·0.968·0.960으로
  쿼리 1~2개 차이라 가르지 못한다. 크기·속도도 셋 다 약 5.7~6억 파라미터·1024차원으로 비슷하다(Arctic·bge-m3는 XLM-R large 계열 인코더, Qwen3는
  디코더 28층 + query 지시문). **val 품질로는 v1을 고를 근거가 없다.**
- 학습 효과는 계열마다 다르다: Qwen3 +0.034, bge-m3 +0.042(둘 다 유의), Arctic +0.009. Arctic-KO는 zero-shot이 이미 학습한 Qwen3와 같다(0.952 vs 0.953).
- Arctic lee의 숫자는 **낙관적으로 편향**돼 있다: val 공식 nDCG로 11개 설정 중 1등을 골랐고(Dwork et al. 2015 — 같은 holdout으로 반복 선택하면 과적합),
  학습이 30 step·lr 5e-6이라 사실상 zero-shot이다. 선택 과정의 편향은 bge-m3 mj(기본값 1회) < kse16(kse14→kse16 2회) < Arctic lee(11회) 순으로 작다.
- 유형별(nDCG@10): 구어·문장(T4, 37개) Arctic 0.944 > bge 0.923 ≈ kse16 0.922 / 개념확장(T3, 12개) bge 0.948 > kse16 0.933 > Arctic 0.926 — 쿼리 수가 적어 방향만 참고.

**후보 조건 차이**: kse16·bge-m3는 현재 학습 데이터(215 쿼리, T4 fp16), Arctic lee는 오타 비활성 전 데이터(sha `067e4aa4`, 237 쿼리)·L4 bf16.
bge-m3 mj의 run 폴더(manifest·가중치)는 2026-10-16에 받아 `models/`·`results/finetune_runs/`에 가져왔다(train data `ec3a9b61`, 416 step, T4 fp16).

**선택(③, 2026-10-16): 임베딩 v1 = bge-m3 mj** (`bge_m3_ft_mj_20261014_0743`). val 품질은 세 후보가 같은 수준이라 운영 기준으로 골랐다 —
기관 공개 베이스(BAAI, MIT)에 우리 판정 데이터로만 학습해 출처를 끝까지 추적할 수 있고(Arctic-KO는 개인 파인튜닝판·AI Hub 학습 데이터 약관 미확인),
선택 과정의 편향이 가장 작다(기본값 1회). 인코더(XLM-R large)라 query 지시문이 없고, Arctic과 계산 비용은 같다.

**남은 일**: 이 모델만 노트북 15번으로 test run → `final_v1_test` 라운드(test 상위 10개 미판정만) 판정
→ test 1회 채점·보고. test 결과를 보고 다시 고르지 않는다.

## 2. 전체 진행 순서와 통과 기준

| 단계 | 할 일 | 통과 기준 / 산출물 |
|---|---|---|
| ① 후보 수집 | **임베딩 모델만**: kse16, 팀원 bge-m3·Arctic 최고 run의 **val+test run** 수집 | `configs/benchmark/judging_candidates.yaml` 등록 |
| ② 일괄 판정 1회 (val 완료 2026-10-16, `final_v1_val`) | 후보 상위 10개 중 판정 안 된 (쿼리, 가맹점)만 A·B 판정 → 조정 → qrels 갱신 | val·test Judged@10 ≥ 0.95(모든 후보) |
| ③ 임베딩 v1 선택 | val 공식 지표로 1개 선택, **test는 그 1개만 1회** 채점 | 선택 근거·test 결과 보고, v1 고정 |
| ④ 검색 파이프라인 | 위치 필터·정렬(거리, 필요시 인지도), **하이브리드 결합, reranker 여부(지연 예산)** — 사전 탐색 결과(1절)를 출발점으로, **벡터 DB/ANN 색인**, BM25 폴백 | ANN recall(exact 대비), 지연 p95 측정 |
| ⑤ 전체 성능 측정 | 실제형 쿼리(로그가 없으므로 팀이 시나리오 기반으로 새로 작성, 7절) + 검색 위치. 반경 안 정답은 소수라 업종·키워드 필터 + 여러 시스템 pooling으로 **거의 빠짐없이** 판정 → 정밀도·재현율 | 쿼리 500개 이상에서 bad@3 상한 ≤ 목표, 현행 대비 우위 |
| ⑥ 부족하면 재학습 | ⑤의 실패 **유형**에 맞춰 실제 쿼리 기반 데이터·코퍼스 기반 합성 데이터로 v2 학습 | ⑤ 지표로 비교 |
| ⑦ 서비스 연결 | 운영 색인·모니터링·폴백 → shadow → interleaving/A/B → 단계적 확대 | 온라인 지표(클릭률, 결과 없음 비율, 재검색률) |

벡터 DB는 ⑦이 아니라 ④에 넣는다 — ANN 색인은 exact 검색과 결과가 조금 달라서, ⑤의 전체 성능은 ANN을 붙인 상태로 재야 한다.

### 3-2. 팀원 run 고르는 기준(판정 없이)
- 노트북 리더보드의 서비스 지표 **nDCG@10(판정만)** 이 가장 높은 run, 비슷하면 bad@3·1위 정답률이 좋은 run.
- Judged@10이 0.95 미만이면 공식 nDCG가 낮게 나온 것이므로 공식 nDCG로 탈락시키지 않는다.
- 어떤 학습 데이터로 학습했는지(manifest `training_data.sha256`)를 NOTE에 남긴다. 오타 비활성 전 데이터(237 쿼리)로 학습한 run도 후보가 될 수 있다
  (학습은 train 업종만 쓰므로 val/test 누설은 없다). 평가는 현재 qrels 기준이어야 하므로 노트북 16번 재채점 후 리더보드를 본다.
- 다만 예전 데이터 run과 현재 데이터 run을 비교하면 "모델 차이"와 "데이터 차이"가 섞인다(kse13→kse14에서 그 차이는 Δ −0.005로 잡음 수준).
  **최종 후보로 올릴 run은 가능하면 같은 설정으로 현재 데이터(sha `ec3a9b61`)로 다시 학습**하고, 어렵다면 NOTE에 데이터 sha를 남긴 채 올린다.
  오타 증강(`typo_variants_per_query`)은 켜지 않는다.

### 3-3. 등록
`configs/benchmark/judging_candidates.yaml`의 `candidates`에 name·note·val·test 경로를 적는다. 노트북 15번 결과처럼 val+test가 한 파일이면
val·test에 같은 경로를 적는다. 후보는 넉넉히 넣어도 된다 — 이미 판정된 쌍은 다시 판정하지 않아 비용은 새로 나온 문서만큼만 는다.

## 4. 일괄 판정 (②) — 명령과 순서

```bash
# 1) 후보 검증 + depth별 판정 건수(아무것도 쓰지 않음)
python scripts/collect_judging_candidates.py
# 2) depth(기본 10)를 확인하고 시트 생성 → benchmark/storesearch_ko_v1/annotations/final_v1/annotation_A.csv, annotation_B.csv
python scripts/collect_judging_candidates.py --make --reason "임베딩 v1 후보 일괄 판정"
# 3) A·B가 서로 모르게 판정 → annotations/final_v1/completed/annotation_A_completed.csv, annotation_B_completed.csv
python scripts/16_supplemental_round.py merge --round final_v1     # 불일치 → analysis/adjudication_needed_only.csv 조정 → 다시 merge
python scripts/11_build_qrels.py
python scripts/12_validate_benchmark.py --stage final
python scripts/rescore_evaluations.py                                # 저장소의 기존 평가 다시 채점
python scripts/pack_for_colab.py                                     # Drive data/ 교체 → 노트북 16번(Drive 평가 다시 채점)
```

- 판정 시트에는 시스템 이름·순위가 없고 행 순서가 섞여 있다(판정자 편향 방지). 판정 기준은 기존 가이드라인 그대로.
- AI 초안은 가이드라인 v1.2대로 참고만 하고 점수는 사람이 확정한다. **A·B가 같은 AI 초안을 함께 보지 않는다** — 둘이 독립이 아니면
  일치도가 부풀려지고 조정할 행이 빠진다(supplement_v2 때처럼 한 명만 쓰거나, 각자 따로 만든 초안을 쓴다).
- 규모 예상: kse14는 이미 거의 판정돼 있었다(val depth 10에서 새 쌍 6개). kse16도 Judged@10 0.994로 거의 판정돼 있다(val 상위 10개 중 미판정 8쌍). 다른 계열 학습 run(bge-m3·Arctic)은 zero-shot이 pool에 있어서 대부분
  덮이지만 쿼리당 몇 개씩 새로 나온다 — 정확한 수는 `collect_judging_candidates.py` 표로 확정한다. (참고: 하이브리드·reranker까지 넣었다면 val만 284쌍)
- 판정은 이 라운드 한 번. 끝난 뒤 판정을 고치거나 val을 보며 다시 판정하지 않는다.

## 5. 선택 규칙 (③)

1. 판정 뒤 val 공식 지표로 비교: nDCG@10(95% CI), Judged@10, bad@3, 1위 정답률, 기준(kse16) 대비 Δ·p.
2. "더 낫다"는 Δ ≥ 0.03이고 p < 0.05일 때만. 그보다 작은 차이는 **같은 수준**으로 본다.
3. 같은 수준이면 서비스 지표(bad@3, 1위 정답률)가 나은 쪽, 그것도 비슷하면 **작고 빠른 모델**(추론 지연·메모리)을 고른다.
4. 고른 모델 1개만 test 1회 채점해 보고한다. test를 보고 다시 고르지 않는다.

## 7. 실제형 평가셋 만들기 (⑤, 검색 로그가 없으므로 팀이 직접 작성)

로그가 없을 때의 표준은 TREC처럼 **정보 요구(상황)를 먼저 쓰고 그에 맞는 쿼리를 쓰는 것**, 그리고 같은 상황에 여러 사람이 각자 쿼리를 써서 표현
다양성을 확보하는 것이다(UQV100, Bailey et al. SIGIR 2016 — 같은 요구에도 사람마다 쿼리가 달라 시스템 순위가 바뀐다). 지금 벤치마크는 "업종 목록 →
쿼리"로 만들어서 업종 의도 쿼리에 치우쳐 있다. 새 셋은 그 편향을 피한다.

### 7-1. 만드는 방식
1. **작성자**: 모델 개발을 직접 하지 않은 팀원 2~3명이 서로 보지 않고 쓴다. 작성 중 검색 결과·코퍼스를 보지 않는다(시스템이 잘하는 쿼리만 쓰게 됨).
2. **상황 카드 → 쿼리**: "토요일 오전, 집 근처에서 아이 운동화 밑창 수선" 같은 상황을 먼저 쓰고, 그 상황에서 이 앱에 칠 검색어를 쓴다.
   같은 상황 카드에 작성자마다 쿼리를 하나씩 → 표현 변형이 자연스럽게 생긴다.
3. **유형 배분(제안, 로그가 생기면 그 분포로 교체)**:

| 유형 | 비율 | 예 | 지금 벤치마크 |
|---|---|---|---|
| 업종·품목 키워드 | 30% | 꽃집, 철물 | 있음(대부분) |
| 메뉴·상품 단위 | 20% | 마라탕, 운동화, 보쌈 | 일부 |
| 상황·구어형 | 15% | 애 생일 케이크 살 데 | 일부(T4) |
| 상호명·체인명 | 15% | 교촌치킨, ○○약국 | 없음 |
| 지역 + 업종 | 10% | 천안 신부동 미용실 | 없음 |
| 속성 | 10% | 카드 되는 정육점, 제로페이 되는 카페 | 없음 |

   속성은 코퍼스에 있는 것(카드·모바일 결제 가능 여부 등)과 없는 것(24시, 주차)을 섞어 "데이터에 없는 조건"을 어떻게 처리하는지도 본다.
4. **업종 표본**: 코퍼스 가맹점 업종 분포에 비례해 뽑고, 드문 업종(꼬리)도 일부 넣는다(층화). 기존 72개 업종 쿼리와 같은 문장은 쓰지 않는다.
5. **검색 위치**: 쿼리마다 위치 1개 — 가맹점 밀도로 나눈 지점(도심·주거지·지방 소도시)에서 층화 추출, 반경 1~3km.
6. **오타**: 일부러 넣지도, 작성자가 실수로 낸 것을 지우지도 않는다(실제 분포 그대로 두고 따로 집계).
7. **판정**: 반경 안에서 업종·키워드 필터 + 후보 시스템 상위 결과를 모아(pooling) 판정. 한 명이 판정하고 20%는 이중 판정해 일치도를 잰다
   (val/test gold보다 가볍게 — 업계의 실제 쿼리 평가 관행). AI 초안은 위 규칙대로.
8. **분할**: dev(파이프라인 조정 — 반경, 하이브리드 가중치, reranker 여부, 점수 기준선)와 test(최종 1회). test는 조정에 쓰지 않는다.

### 7-2. 몇 개 만들까 — 지금 데이터의 분산으로 계산
| 목적 | 필요한 쿼리 수 |
|---|---|
| 두 구성의 nDCG@10 차이 0.02 구분(α 0.05, 검정력 0.8) | 약 130 |
| 차이 0.01 구분 | 약 515 |
| bad@3 ≤ 5% 입증(실제 3%일 때) | 약 280 |

→ **test 300개 + dev 150~200개, 총 450~500개**를 목표로 한다. 시작은 test 200 + dev 100(총 300)으로 하고, 결과의 신뢰구간이 목표를 가르지 못하면
늘린다. 판정량은 쿼리당 40~60쌍 정도로 보면 300개에 1.2만~1.8만 쌍 — AI 초안 + 1인 판정 + 20% 이중 판정으로 줄인다.
