# 서비스형 쿼리셋 v1 (2026-10-19)

기존 벤치마크(업종 의도 72개, 548개 쿼리)는 업종명을 보고 쓴 쿼리라 실제 사용자 쿼리의 큰 부분을 재지 못한다
(`docs/SERVICE_READINESS.md` 1절). 그래서 쿼리 종류를 넓힌 별도 셋을 만든다. 기존 벤치마크의 train/val/test는 그대로 둔다.

## 1. 무엇을 몇 개 (1차 500개, 2026-10-19 결정)

| 묶음 | 목표 | 내용 | 작성 재료(템플릿 시트) |
|---|---|---|---|
| A 업종 확장 | 150 | 기존 셋에 없는 업종·품목(태권도, 보청기, 마라탕, 식육…)과 질의 1~2개뿐인 기존 업종 | `A_업종후보` |
| B 상호명·브랜드 | 150 | 체인(GS25↔지에스25, BBQ↔비비큐), 개별 상호의 전체·일부·지점명 | `B_가맹점표본`, `B_체인목록` |
| C 상품·상황 | 130 | 업종명 없이 상황만 보고 쓴 쿼리 | `C_상황카드` |
| D 지역+업종 | 50 | "망원시장 떡집", "강남 치킨" | `D_시장표본` |
| E 결과 없음 | 20 | 가맹점이 아닐 법한 대상(코스트코, 영화관) | `E_결과없음후보` |

오타는 넣지 않는다(철자 교정은 앞단 처리 — `configs/benchmark/inactive_queries_v1.yaml` 머리말).

**개수 근거**
- bad@3 ≤ 0.05를 판별하려면, 실제 값이 0.03일 때 test가 약 300개 필요하다.
- nDCG Δ 0.02를 구분하려면 약 130개, Δ 0.01이면 약 500개가 필요하다. final_v1_val 비교에서 쿼리별 차이의 표준편차가 약 0.08이었던 것을 바탕으로 추정했다.
- 묶음별로 결론을 내려면 묶음마다 test가 100개 이상 필요하다. 그래서 B·C를 늘렸다. A는 112, B는 112, C는 약 98개가 된다.
- D·E는 test가 각각 약 38개, 15개라 묶음 결론을 낼 수 없다. 이 두 묶음은 큰 실패가 있는지 확인하는 용도로만 쓴다.
- 2차로, 검색 로그를 확보하면 로그에서 빈도 구간별로 층화 추출해 500개를 더한다. 이때 위의 묶음 비율 자체를 로그 분포에 맞게 고친다.

## 2. split — 평가 전용

- **사람이 쓴 쿼리는 학습에 쓰지 않는다.**
  - 기존 train 237개에 100여 개를 더해도 학습 신호가 작다. 오타 증강 학습도 Δ +0.001(p=0.70)이었다.
  - 반면 이 쿼리를 train에 쓰면 평가 정밀도를 잃는다.
- **dev 125 / test 375로 나눈다.** 묶음마다 25% / 75%이고, A의 새 업종은 업종 단위로, B~E는 쿼리 단위로 나눈다.
- **dev의 용도**: 개발 중 지표 확인, 실패 유형 파악.
- **test의 용도**: 일괄 판정을 끝낸 뒤 결정 시점에 한 번 채점한다(EVALUATION_POLICY 1절). 학습·튜닝에는 쓰지 않는다.

## 3. 작성 원칙

사람이 직접 쓰는 절차와 작성자 안내문은 `docs/QUERY_WRITING_GUIDE.md`에 있다.

1. **각자 따로 쓴다.** 5명 이상, 팀 밖 사람을 포함한다. 서로의 쿼리를 보지 않는다.
2. **C는 카드만 보고 쓴다.** 업종 목록이나 코퍼스를 보면 그 단어를 베낀다. 기존 셋이 T1·T2에 쏠린 원인이 이것이다.
3. **B는 가맹점에서 거꾸로 쓴다.** 표본 가맹점을 보고 "이 가게를 찾는다면 뭐라고 칠까"를 쓴다.
   표본의 25%는 취급품목이 비었거나 "음식점"뿐인 가맹점이다. 이런 가맹점은 상호명으로만 찾을 수 있다.
4. **LLM은 후보로만 쓴다.** 작성방식=LLM후보로 표시하고, test에는 직접 쓴 쿼리 중심으로 넣는다.
5. **모든 쿼리에 가정위치를 붙인다.**
   - B는 표본 가맹점 위치, D는 시장(M번호)을 쓴다. A·C·E는 비우면 나중에 자동 배정한다.
   - 위치 기능은 나중에 만들지만, 쿼리셋을 다시 만들지 않도록 위치 맥락은 지금 기록한다.

### 판정과 집계
- 사람은 업종·상호 관련성만 판정한다. 지역 일치는 주소·좌표로 자동 계산한다.
- pool은 시스템 3~4개(bge-m3 mj, BM25, 하이브리드, zero-shot)의 상위 20개씩이다. 쿼리당 약 45개, 전체 약 2.2만 쌍이 된다.
- A·B 이중 판정은 20%에만 한다(일치도 확인용). 나머지는 1인 판정 + AI 초안으로 한다.
  AI 초안은 판정자 한 명만 본다(EVALUATION_POLICY 1절).
- **판정 전에 가이드라인을 보완해야 한다.** 상호명 쿼리의 등급("교촌" → 모든 지점? 가까운 지점?)과 E 묶음의 판정 기준이 아직 없다.
- 묶음별로 따로 보고한다. D는 위치 기능이 생기기 전에는 기준점으로만 쓰고, 주 지표에 섞지 않는다.

## 4. 실행

```bash
python scripts/make_service_queryset_template.py            # data/query/service_queryset_v1.xlsx 생성(있으면 안 덮어씀)
python scripts/make_service_queryset_template.py --dry-run  # 시트별 행 수만 확인
```

- 설정(목표 개수, split, 상황 카드, 브랜드 별칭, seed)은 `configs/query/service_queryset_v1.yaml`에 있다.
- 템플릿을 배포한 뒤에는 seed를 바꾸지 않는다. 바꾸면 표본ID(S·M번호)가 다른 가맹점을 가리키게 된다.

### 작성 결과 가져오기 (2026-10-20)

```bash
python scripts/import_service_queries.py --dry-run   # 묶음 × split 개수, 제외·중복 요약만
python scripts/import_service_queries.py             # → data/query/service_queries_v1.csv (+ .meta.json)
```

- **입력**
  - 작성자 완료본 `data/query/writers_completed/서비스셋_직접작성_v1_3명_completed.xlsx`: W1~W3의 A·C·D·E
  - 팀 작성본 `data/query/service_queryset_v1_team_completed.xlsx`: 사람이 쓴 B 150개만 쓴다. 나머지 A·C·D·E 350개는 AI 초안이라
    쓰지 않는다(2026-10-20 결정 — 합성 학습 데이터 계획을 접어 생성 예시로 쓸 곳도 없음).
  - 설정 `import.extra_queries`: 진행자가 직접 더한 쿼리(`writers=facilitator`). 지금은 E 3개(신세계, 샤넬, 5성급 호텔)
- **같은 쿼리 합치기**: 공백을 지우고 소문자로 바꿔 같은 문자열이면 한 쿼리로 합친다. 몇 명이 썼는지는 `n_writers`·`writers`에 남긴다.
  여러 묶음에 나오면 B > D > C > A > E 순서로 앞 묶음에 두고, 나머지는 `also_in_bundles`에 적는다.
- **제외**(`status=excluded`): 다음 두 경우다. 행은 지우지 않는다.
  - 기존 벤치마크 **train** 쿼리와 같은 문자열. 학습에 쓰인 문자열이라 v1에 유리하다.
  - 설정 `import.exclude_queries`에 적은 쿼리. 판정 결과 E가 아닌 것 등을 여기에 적는다.
  기존 val/test와 같은 문자열은 `old_benchmark_split`에 표시만 한다.
- **dev/test**: 묶음마다 약 25% / 75%로 나눈다. 같은 근거(A 업종, C 카드, B 가맹점, D 시장)의 쿼리는 같은 쪽에 둔다.
  dev에서 본 카드나 업종이 test에 다시 나오면 dev로 맞춘 튜닝이 test에 새기 때문이다.
- **가정위치**
  - D: 고른 시장
  - B 개별 가맹점: 표본 가맹점 좌표
  - B 브랜드: 작성자가 고른 시장
  - A·C·E: 쿼리 문자열 해시로 고른 표본 시장(`location_source=auto`)
  - B 개별 가맹점 쿼리의 지역 부분("묵동 대박축산"의 "묵동")은 주소·시장명과 맞춰 자동으로 채운다(`region_text_source=auto`).
    상호의 지점명과 겹치는 지역("안산 고잔 숯토리" → 지점 "안산고잔점")은 잡지 못한다.
- **E**: `corpus_hits`에 상호·취급품목에서 그 문자열이 몇 번 나오는지 적는다. 많이 나오는 것(백화점 621, 명품 419 등)은 판정 결과에 따라 제외하거나 A로 옮긴다.
- **1차 결과(2026-10-20)**: 입력 503줄 → 쿼리 498개(중복 5개 합침), 제외 3개(기존 train과 같음: 머리 자르는 곳, 반찬가게, 반찬 사는 곳).

  | 묶음 | dev | test |
  |---|---|---|
  | A | 40 | 108 |
  | B | 38 | 112 |
  | C | 34 | 92 |
  | D | 13 | 38 |
  | E | 5 | 15 |


### 판정 pool 만들기 (반경 안)

판정 기준은 `docs/SERVICE_ANNOTATION_GUIDELINE.md`에 있다. 판정은 반경 2km 안 가맹점으로 하고, 채점은 1km(현재 서비스)와 2km로 한다.

```bash
python scripts/build_service_pool.py export          # 반경 안 가맹점 129,608개·쿼리 → colab_upload/service_eval/ (Colab 입력)
#   Colab: colab/service_dense_runs.ipynb → bge_m3_ft_mj_20261014_0743.csv, bge_m3.csv → benchmark/service_ko_v1/runs/
python scripts/build_service_pool.py runs            # char BM25·키워드 후보 run(로컬, 약 3분)
python scripts/build_service_pool.py pool --dry-run  # depth별 판정 건수
python scripts/build_service_pool.py pool --round service_v1 --depth 10
```

- BM25·키워드 후보 쿼리에서는 서술어('파는', '곳')와 지역 표현을 뺀다. 후보가 이미 반경 안이라, 지역 단어를 남기면 지점명이 같은
  아무 가게나 끌려오기 때문이다.
- BM25·키워드 두 run만으로 잰 판정 건수: depth 10이면 5,272쌍(쿼리당 10.6), depth 20이면 10,097쌍. 임베딩 run 두 개를 더하면 늘어난다.
