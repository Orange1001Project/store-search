# 서비스형 쿼리셋 v1 (2026-10-19)

기존 벤치마크(업종 의도 72개, 548개 쿼리)는 업종명을 보고 쓴 쿼리라 실제 사용자 쿼리의 큰 부분을 재지 못한다
(`docs/SERVICE_READINESS.md` 1절). 그래서 쿼리 종류를 넓힌 별도 셋을 만든다. 기존 벤치마크의 train/val/test는 그대로 둔다.

## 1. 무엇을 몇 개 (1차 500개, 2026-10-19 결정)

| 묶음 | 목표 | 내용 | 작성 재료(템플릿 시트) |
|---|---|---|---|
| A 업종 확장 | 150 | 기존 셋에 없는 업종·품목(태권도, 보청기, 마라탕, 식육…)과 질의 1~2개뿐인 기존 업종 | `A_업종후보` |
| B 상호명·브랜드 | 150 | 체인(GS25↔지에스25, BBQ↔비비큐), 개별 상호의 전체·일부·지점명 | `B_가맹점표본`, `B_체인목록` |
| C 상품·상황 | 130 | 업종명 없이 상황만 보고 쓴 쿼리 | `C_상황카드` |
| D 지역+업종 | 50 | "망원시장 떡집", "강남 치킨" | `D_시장표본` |
| E 결과 없음 | 20 | 가맹점이 아닐 법한 대상(코스트코, 영화관) | `E_결과없음후보` |

오타는 넣지 않는다(철자 교정은 앞단 처리 — `configs/benchmark/inactive_queries_v1.yaml` 머리말).

**개수 근거**
- bad@3 ≤ 0.05를 판별하려면, 실제 값이 0.03일 때 test가 약 300개 필요하다.
- nDCG Δ 0.02를 구분하려면 약 130개, Δ 0.01이면 약 500개가 필요하다. final_v1_val 비교에서 쿼리별 차이의 표준편차가 약 0.08이었던 것을 바탕으로 추정했다.
- 묶음별로 결론을 내려면 묶음마다 test가 100개 이상 필요하다. 그래서 B·C를 늘렸다. A는 112, B는 112, C는 약 98개가 된다.
- D·E는 test가 각각 약 38개, 15개라 묶음 결론을 낼 수 없다. 이 두 묶음은 큰 실패가 있는지 확인하는 용도로만 쓴다.
- 2차로, 검색 로그를 확보하면 로그에서 빈도 구간별로 층화 추출해 500개를 더한다. 이때 위의 묶음 비율 자체를 로그 분포에 맞게 고친다.

## 2. split — 평가 전용

- **사람이 쓴 쿼리는 학습에 쓰지 않는다.**
  - 기존 train 237개에 100여 개를 더해도 학습 신호가 작다. 오타 증강 학습도 Δ +0.001(p=0.70)이었다.
  - 반면 이 쿼리를 train에 쓰면 평가 정밀도를 잃는다.
  - 학습 데이터는 4절의 합성 방식으로 만든다.
- **dev 125 / test 375로 나눈다.** 묶음마다 25% / 75%이고, A의 새 업종은 업종 단위로, B~E는 쿼리 단위로 나눈다.
- **dev의 용도**: 개발 중 지표 확인, 합성 생성 프롬프트의 예시, 실패 유형 파악.
- **test의 용도**: 일괄 판정을 끝낸 뒤 결정 시점에 한 번 채점한다(EVALUATION_POLICY 1절). 생성 프롬프트에도 쓰지 않는다.

## 3. 작성 원칙

1. **각자 따로 쓴다.** 5명 이상, 팀 밖 사람을 포함한다. 서로의 쿼리를 보지 않는다.
2. **C는 카드만 보고 쓴다.** 업종 목록이나 코퍼스를 보면 그 단어를 베낀다. 기존 셋이 T1·T2에 쏠린 원인이 이것이다.
3. **B는 가맹점에서 거꾸로 쓴다.** 표본 가맹점을 보고 "이 가게를 찾는다면 뭐라고 칠까"를 쓴다.
   표본의 25%는 취급품목이 비었거나 "음식점"뿐인 가맹점이다. 이런 가맹점은 상호명으로만 찾을 수 있다.
4. **LLM은 후보로만 쓴다.** 작성방식=LLM후보로 표시하고, test에는 직접 쓴 쿼리 중심으로 넣는다.
5. **모든 쿼리에 가정위치를 붙인다.**
   - B는 표본 가맹점 위치, D는 시장(M번호)을 쓴다. A·C·E는 비우면 나중에 자동 배정한다.
   - 위치 기능은 나중에 만들지만, 쿼리셋을 다시 만들지 않도록 위치 맥락은 지금 기록한다.

### 판정과 집계
- 사람은 업종·상호 관련성만 판정한다. 지역 일치는 주소·좌표로 자동 계산한다.
- pool은 시스템 3~4개(bge-m3 mj, BM25, 하이브리드, zero-shot)의 상위 20개씩이다. 쿼리당 약 45개, 전체 약 2.2만 쌍이 된다.
- A·B 이중 판정은 20%에만 한다(일치도 확인용). 나머지는 1인 판정 + AI 초안으로 한다.
  AI 초안은 판정자 한 명만 본다(EVALUATION_POLICY 1절).
- **판정 전에 가이드라인을 보완해야 한다.** 상호명 쿼리의 등급("교촌" → 모든 지점? 가까운 지점?)과 E 묶음의 판정 기준이 아직 없다.
- 묶음별로 따로 보고한다. D는 위치 기능이 생기기 전에는 기준점으로만 쓰고, 주 지표에 섞지 않는다.

## 4. 학습 데이터 — 코퍼스 기반 합성 (미착수)

사람이 쓴 쿼리 대신 코퍼스 21만 가맹점에서 서비스 쿼리 유형의 학습 쿼리를 수천~수만 개 만든다.
근거가 되는 방법은 다음과 같다.
- doc2query(Nogueira 2019), InPars(Bonifacio 2022): 문서에서 쿼리를 생성한다.
- Promptagator(Dai 2023): 예시 몇 개로 생성하고, 왕복 일치로 거른다.
- GPL(Wang 2022): cross-encoder 점수를 소프트 라벨로 쓴다.
- RocketQA(Qu 2021): cross-encoder로 거짓 오답을 제거한다.

### 4-1. 묶음별 생성 방법

| 묶음 | 생성 | 정답(positive) | 비고 |
|---|---|---|---|
| B 상호명 | **규칙**. 전체 상호, 지점명 뺀 상호, 첫 토큰(브랜드), 별칭(`chain.aliases`), 띄어쓰기 변형 | 그 가맹점. 브랜드만 친 쿼리는 같은 브랜드 전체 — 가이드라인 결정을 따른다 | LLM이 필요 없고 정답이 확실하다. 동명 가맹점(형제상회)은 정답이 여러 개 |
| A 업종·품목 | **LLM**. 가맹점(상호+취급품목)을 주고 "이 가게를 찾을 때 칠 말"을 2~3개 생성. T2·T3·T4·T5 유형을 지정 | 생성한 가맹점 + 4-2의 정답 확장 | 예시는 기존 train 쿼리와 dev에서 뽑는다 |
| C 상황 | **LLM**. 가맹점을 주고 "이 가게가 필요해지는 상황에서 칠 말"을 생성 | 같음 | 예시는 dev의 C 쿼리. 상황 카드 문장은 쓰지 않는다(test와 같은 카드라서) |
| D 지역+업종 | 임베딩 학습에 **쓰지 않는다** | — | 지역은 쿼리 파서와 필터가 처리한다. 대신 파서용 데이터를 만든다(시장명·시군구·동 + 업종 → 지역 태그) |
| E 결과 없음 | 쓰지 않는다 | — | 점수 임계값(결과 없음 판단)을 보정할 때 dev로만 쓴다 |

### 4-2. 거르기와 라벨링 — 업종 쿼리는 정답이 여러 개라 이 단계가 핵심
1. **왕복 일치(Promptagator).** v1과 BM25로 생성 쿼리를 검색해, 원래 가맹점이 상위 20위 안에 없으면 버린다(생성이 엉뚱한 경우).
2. **정답 확장과 거짓 오답 제거(RocketQA).** "치킨 먹을 데"는 원래 가맹점 말고도 치킨집 수천 곳이 정답이다.
   그래서 v1 상위 50개를 cross-encoder(bge-reranker-v2-m3)로 채점한다.
   - 높은 점수: 정답으로 추가
   - 중간 점수: 버림(애매함)
   - 낮은 점수: hard negative
   - 임계값은 기존 train qrels(사람 판정)에서 정밀도 0.9가 되는 점으로 정한다.
3. **또는 GPL 방식.** 정답·오답을 나누지 않고 cross-encoder 점수 차이를 그대로 학습한다(MarginMSE). 정답이 여러 개인 쿼리에 잘 맞는다.
   두 방식은 dev로 비교한다.
4. **누수 차단.**
   - 기존 벤치마크 val·test 업종과 서비스셋 test의 새 업종(A)에 해당하는 생성 쿼리는 뺀다.
   - test 쿼리와 정규화 문자열이 같거나, 임베딩 유사도가 매우 높은(예: 0.95 이상) 생성 쿼리도 뺀다.

### 4-3. 규모와 학습
- **시작 규모**: 가맹점 1만 곳 × 2~3개, 약 2~3만 쿼리. 가맹점은 시장유형·업종 비율대로 뽑되, 상호명만 있는 가맹점을 포함한다.
- **학습 구성**: 기존 사람 train 237개(가중치를 높임) + 합성 데이터로 v1(bge-m3 mj) 설정 그대로 이어서 학습한다.
  5천 / 2만 개 두 규모로 dev 곡선을 본다.
- **평가**: 기존 val + 서비스셋 dev로 고르고, 서비스셋 test로 한 번 보고한다.
- **GPU 작업은 Colab에서 한다(2026-10-19 결정).**
  - 대상: LLM 생성, cross-encoder 채점, 학습.
  - 생성 모델: 오픈 LLM(Qwen3-8B, EXAONE 계열 등)을 Colab GPU에서 돌린다. 3만 개 생성은 GPU 몇 시간 규모(추정)다.
  - 데이터 흐름: 기존 `colab/rerank_scores.ipynb`처럼 로컬에서 입력 CSV를 만들어 Drive `store-search-ai/`에 올리고, 결과 CSV를 받아 로컬에서 거르기·조립을 한다.
  - Colab은 Google 서버라서 가맹점 데이터가 기관 밖으로 나간다. 기존 학습·채점에서도 같은 경로를 썼으므로 새로운 노출은 아니다.
    다만 외부 LLM API는 쓰지 않는다(쿼리 생성을 위해 데이터를 또 다른 업체로 보내지 않는다).
- **순서**: B 규칙 생성은 GPU 없이 바로 할 수 있으므로 먼저 하고, A·C LLM 생성은 서비스셋 dev가 생긴 뒤에 한다(예시가 필요하다).

## 5. 실행

```bash
python scripts/make_service_queryset_template.py            # data/query/service_queryset_v1.xlsx 생성(있으면 안 덮어씀)
python scripts/make_service_queryset_template.py --dry-run  # 시트별 행 수만 확인
```

- 설정(목표 개수, split, 상황 카드, 브랜드 별칭, seed)은 `configs/query/service_queryset_v1.yaml`에 있다.
- 템플릿을 배포한 뒤에는 seed를 바꾸지 않는다. 바꾸면 표본ID(S·M번호)가 다른 가맹점을 가리키게 된다.
- 작성이 끝난 xlsx를 쿼리셋으로 가져오는 스크립트(가정위치 자동 배정, dev/test split)는 작성이 끝난 뒤에 만든다.
