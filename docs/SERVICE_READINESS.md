# 서비스 적용 판단 로드맵 (2026-10-15)

지금 벤치마크(val 124 / test 160 쿼리)로 할 수 있는 것과 없는 것, 실제 서비스에 쓸 수 있다고 말하기 위해 무엇이 더 필요한지,
외부 API와 비교해 어떻게 판단할지를 정리한다. 평가·판정 운영 규칙은 `docs/EVALUATION_POLICY.md`.

## 1. 지금 벤치마크의 위치 — "시스템 비교용", "출시 판정용"이 아님

| 한계 | 수치 |
|---|---|
| 통계 정밀도 | kse14 val nDCG@10 0.948, 95% CI [0.921, 0.972]. bad@3 0.097(12/124), 95% CI 약 [0.045, 0.149] — 목표 0.05가 구간 안이라 달성 여부를 판별할 수 없음 |
| 쿼리 분포 | 연구자가 만든 업종 의도 쿼리. 실제 사용자 쿼리의 큰 부분(상호명 "교촌 ○○점", 지역+업종 "강남 치킨", 속성 "24시 약국")을 재지 않음 |
| 업종 범위 | 72개 업종 표본(val 15개). 코퍼스의 서로 다른 취급품목 표현은 32,325개 |

TREC류 평가는 쿼리 50~250개로 **시스템 간 비교**를 한다(Voorhees & Buckley 2002는 쿼리 50개에서 작은 차이를 믿기 어렵다고 분석).
**출시 판단**은 서비스 회사들이 실제 쿼리 수천 개의 사람 평가와 온라인 실험으로 한다. 이 벤치마크에서 목표에 닿으면 "파일럿을 시작할 근거"이지
"서비스 품질이 검증됐다"는 근거가 아니다.

## 2. 서비스에 쓸 수 있다고 말하기까지 — 4단계

### 2-1. 실제 쿼리 평가셋 (가장 중요)
- **원천**: 기존 가맹점 검색(앱·웹)의 검색 로그가 있으면 최우선. 없으면 파일럿에서 수집.
- **표본**: 빈도 구간별 층화 추출 — 자주 나오는 쿼리(head)·중간(torso)·드문 쿼리(tail)를 고루. 500~1,000개 규모가 업계에서 흔하다.
  쿼리 수는 잡아내야 할 차이와 분산으로 정한다(Sakai 2016, *Topic set size design*). 예: Δ 0.02~0.03을 구분하려면 수백 개가 필요.
- **판정**: 같은 가이드라인으로, 후보 시스템들 + **현행 검색**의 상위 결과를 pool로(EVALUATION_POLICY 3절).
- 상호명·지역·속성 쿼리가 많이 나오면 그때 가이드라인과 시스템(필터·정렬)을 함께 확장한다.

### 2-2. 현행 검색과 나란히 비교(side-by-side)
- 같은 쿼리에 대해 현행 결과와 새 결과를 나란히 보여 주고 평가자가 어느 쪽이 나은지(이김/비김/짐) 고른다. 검색 품질 평가자 제도를 둔
  서비스(구글 Search Quality Rater Guidelines 등)와 커머스 검색에서 흔히 쓰는 방식이다. 절대 점수보다 "지금보다 나은가"를 직접 잰다.

### 2-3. 시스템 요건
- 지연시간 p95(쿼리 인코딩 + 검색 + reranker), 21만 문서 ANN 색인(HNSW/FAISS)의 recall이 exact 검색과 얼마나 같은지,
  가맹점 추가·변경 반영 주기, 장애 시 BM25 단독으로 폴백, 품질·지연 모니터링.

### 2-4. 온라인 검증
- **shadow**(실제 트래픽에 새 시스템을 돌리되 결과는 안 보여 줌, 지연·오류 확인) → **interleaving**(두 시스템 결과를 섞어 보여 주고
  클릭으로 선호 판정, Chapelle et al. 2012, TOIS — 적은 트래픽으로도 민감) → **A/B 테스트**(클릭률, 결과 없음 비율, 재검색률, 이탈)
  → 단계적 확대. 최종 판단은 여기서 한다.

## 3. 모델·검색 구성 개선 트랙 (2단계와 병행)

| 방법 | 근거 | 상태 |
|---|---|---|
| 하이브리드(BM25 + 임베딩, RRF) | Cormack et al. 2009; 실무 기본 구성 | val 측정: top1 0.952→0.976, bad@3 12→9(일괄 판정 후보) |
| reranker(검색 후 상위 50개 재정렬) | 2단 구조(검색→재정렬)가 업계 표준 | bge-reranker-v2-m3: 판정만 nDCG 0.953(기준과 같음). Qwen3-Reranker 측정 중 |
| 코퍼스 기반 대규모 합성 학습 데이터 | doc2query(Nogueira 2019), InPars(Bonifacio 2022), Promptagator(Dai 2023), GPL(Wang 2022) | 미착수. val 실패에 맞춘 소량 추가는 하지 않음 |
| hard negative + false negative 정제 | RocketQA(Qu et al. 2021) — cross-encoder로 거짓 오답 제거 | 미착수 |
| reranker → 임베딩 증류 | cross-encoder 점수를 임베딩 학습 신호로(GPL 방식) | 미착수 |
| 쿼리 이해(철자 교정, 지역·상호명 파싱) | 서비스 표준 앞단 처리 | 실제 쿼리 확보 후(오타 쿼리는 비활성, 2026-10-14) |

## 4. 외부 API와 비교

### 4-1. 무엇을 비교하나
외부 임베딩·reranker API(예: OpenAI·Google·Cohere·Voyage 계열 임베딩, Cohere 계열 rerank, 한국어 특화 업체 임베딩 — 이름·가격은
도입 시점에 다시 확인)는 별도 학습 없이 다국어 성능이 좋은 편이다. 반면 우리 구성(Qwen3-Embedding-0.6B LoRA + BM25 + 오픈 reranker)은:

| 축 | 자체 구성 | 외부 API |
|---|---|---|
| 도메인 적응 | 가맹점 데이터로 학습 가능(+0.035 nDCG, kse14) | 학습 불가 또는 제한적 |
| 데이터 반출 | 쿼리·가맹점 데이터가 밖으로 안 나감 | 매 쿼리가 외부로 전송 — 기관 보안 정책·망 분리 확인 필요 |
| 지연·가용성 | 내부망 수~수십 ms, 자체 장애 대응 | 네트워크 왕복 추가, 외부 장애·요금제·모델 교체(교체 시 21만 문서 재색인)에 종속 |
| 비용 구조 | GPU/CPU 서버 고정비 | 문서 색인은 한 번, 쿼리마다 과금 — 트래픽이 크면 누적 |
| 라이선스 | Qwen3-Embedding·Qwen3-Reranker(Apache 2.0), bge-m3·bge-reranker(MIT) 상업 이용 가능 | 약관 |

### 4-2. 판단 방법
1. **같은 벤치마크로 잰다**: API 모델의 val·test run을 만들어 **일괄 판정 후보로 등록**한다(EVALUATION_POLICY 3절). API 모델은 pool에 없던
   계열이라 판정 없이는 점수가 낮게 나온다 — 판정 전 공식 점수로 비교하면 안 된다. 문서 임베딩 비용은 21만 개 × 수십 토큰이라 크지 않다
   (외부 전송 허용 여부를 먼저 확인).
2. **API가 더 좋으면 따라잡는 방법**
   - 더 큰 오픈 모델(Qwen3-Embedding-4B/8B)이나 오픈 reranker로 격차를 줄인다(하이브리드 + reranker가 보통 가장 크게 메움).
   - API를 "선생"으로 쓴다: 코퍼스 기반 합성 쿼리에 API 임베딩·reranker 점수를 매겨 그 순서를 학습 신호로 Qwen3-0.6B를 학습(GPL 방식 증류).
     서비스에서는 자체 모델만 쓰므로 운영 중 외부 전송이 없다(학습 데이터 생성 때만 API 사용 — 약관 확인).
3. **자체 구성이 비슷하거나 낫다면** 4-1의 데이터 반출·지연·종속 측면에서 자체 구성이 유리하다.

## 5. 실행 순서

1. Qwen3-Reranker 측정 완료(Colab) → 유망 구성 확정(판정 없이, EVALUATION_POLICY 2절)
2. 후보(kse14, kse14 하이브리드, reranker 구성, 필요하면 API 모델 1~2개)의 val·test run 생성 → **일괄 판정 1회**
3. 최종 구성 1개를 val로 고르고 test 1회 보고 — "파일럿 근거" 확보
4. 지연·색인·폴백 등 시스템 요건 측정(2-3)
5. 실제 쿼리 확보(로그 또는 파일럿) → 실제 쿼리 평가셋 + 현행 대비 side-by-side(2-1, 2-2)
6. shadow → interleaving/A/B(2-4)
7. 병행: 코퍼스 기반 합성 데이터·hard negative 정제·증류(3절)는 5번에서 실제 실패 유형을 본 뒤 우선순위를 정한다
