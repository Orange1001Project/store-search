# DB 설계 이유서

> 기준: `docs/DB_DESIGN.md` v0.3.2(테이블 19개) · `docs/db/schema.sql`
> 이 문서는 **왜 이렇게 설계했는지**를 적는다. 무엇이 있는지는 [`DB_TABLES.md`](DB_TABLES.md)(테이블·컬럼 설명), 전체 명세는 [`../DB_DESIGN.md`](../DB_DESIGN.md)를 본다.
> 결정의 출처는 요구사항(`docs/REQUIREMENTS.md` 4절 DR)과 팀 결정(2026-11-10 ~ 11-13)이다.

## 1. 출발점: 이 서비스 데이터의 성격

설계는 아래 다섯 가지 사실에서 나왔다.

| 사실 | 설계에 준 영향 |
|---|---|
| 가맹점 원천 데이터는 **매주 엑셀 파일 하나로 통째로** 온다(약 21~22만 행) | 원천 값을 매주 덮어쓰는 표와, 검색이 읽는 표를 나눠야 한다 |
| 관리자는 원천 값을 **고칠 수 있고**, 고친 값이 원천보다 우선한다 | 고친 값은 원천과 따로 둬야 매주 덮어써도 살아남는다 |
| 검색은 **버전이 섞이면 안 되고** 갱신 중에도 멈추면 안 된다 | 버전별 완성본을 미리 만들고 한 번에 바꾼다 |
| 평가 정답이 **기존 `store_id`(UUID)** 로 연결되어 있다 | 이미 발급한 번호는 절대 바꾸지 않는다 |
| 검색 로그가 하루 수만 건씩 **계속 쌓이고 1년 뒤 지운다** | 쓰기가 가볍고 오래된 것을 통째로 지우기 쉬워야 한다 |

## 2. 큰 결정과 이유

### 2-1. 원천 값(`store`)과 관리자 수정 값(`store_override`)을 나눴다

- **문제**: 관리자가 "가마치통닭"의 QR결제를 '가능'으로 고쳐도, 다음 주 원천 파일이 '불가'로 덮어쓰면 수정이 사라진다.
- **선택**: 원천은 `store`에 매주 덮어쓰고, 고친 값은 `store_override`에 가게 × 필드로 따로 둔다. 검색용 값 = 원천 값 위에 수정 값을 덮은 것.
- **덤**: 고칠 때의 원천 값(`source_value_at_edit`)을 같이 두면, 다음 주 원천이 바뀌었는지 비교해 "원천이 바뀌었어요" 표시를 켤 수 있다.

### 2-2. 검색용 표(`store_snapshot`)를 버전마다 통째로 만든다

- **문제**: 21만 행을 그 자리에서 고치면, 갱신하는 몇 분 동안 검색이 반은 지난주·반은 이번 주 값을 본다.
- **선택**: 새 버전 파티션을 다 채운 다음, 붙이기와 활성 버전 바꾸기를 한 번에 한다. 검색은 언제나 활성 버전 하나만 본다.
- **대가**: 상호·주소가 `store`와 스냅샷 두 곳에 있다(일부러 한 중복, 4절). 저장 공간은 버전당 약 1GB(대부분 벡터)이고 직전 버전 하나만 남긴다.

### 2-3. 행을 지우지 않고 상태로 관리한다

| 표 | 지우는 대신 | 이유 |
|---|---|---|
| `store` | 영업중 → 확인 대기 → 폐업 | 평가 정답·즐겨찾기·로그가 옛 가게를 가리킨다. 지우면 연결이 끊긴다. 다음 주에 돌아오는 가게도 많다 |
| `member` | 상태를 탈퇴로, 개인정보는 비움 | 회원 번호와 가입·탈퇴 시각만 남겨 통계는 유지하되 누구인지는 알 수 없게 |
| `admin_user` | 비활성화 | 수정·숨김 기록이 관리자 번호를 가리킨다 |

### 2-4. 지난 이력은 남기지 않는다

- 수정 이력, 상태 이력, 관리자 접속 기록 표를 두지 않는다(2026-11-13 팀 결정, 필수 테이블만).
- 대신 **지금 값 + 마지막으로 바꾼 사람·시각·사유**는 남긴다(`store_override`, `store.status_changed_at`, `store.visibility_*`).
- 필요해지면 이력 표를 **더하기만** 하면 되고, 지금 표를 바꿀 필요는 없다.

### 2-5. 로그는 `search_log` 하나를 중심으로, 월별로 쌓는다

- 검색 결과 한 페이지 = 한 행. 그때 보여 준 가게 목록은 같은 행의 `results`(JSON 목록)에 넣는다. 가게마다 한 행이면 검색 한 번에 20행이 생긴다.
- 한국 시간 기준 한 달마다 파티션을 나누고, 1년 지난 달은 파티션째 지운다. 행을 하나씩 지우는 것보다 훨씬 빠르다.
- 로그에는 FK를 걸지 않는다(3-4절).

### 2-6. 화면·검색 서버가 자주 읽는 사전은 작은 표로, 바뀌면 1분 안에 반영

- 업종·결제·별칭·지명·제외어·확장어는 검색 서버가 메모리에 올려 쓴다. 표마다 `updated_at`을 두고 1분마다 확인해 바뀐 것만 다시 읽는다.
- 그래서 "버전 번호 표" 같은 관리용 표를 따로 두지 않았다.

## 3. 관계를 이렇게 정한 이유

### 3-1. 읽는 법

| 표기 | 뜻 | 예 |
|---|---|---|
| 1 : 1 | 한쪽 하나에 다른 쪽도 딱 하나 | (이 설계에는 없다. 3-3절) |
| 1 : N | 부모 하나에 자식 여러 개, 자식은 부모 하나만 | 회원 1명 : 로그인 수단 여러 개 |
| N : M | 양쪽 모두 여러 개와 이어짐. 가운데 연결 표가 필요 | 회원 여러 명 ↔ 가게 여러 곳(즐겨찾기) |
| FK | "이 값은 부모 표에 꼭 있어야 한다"는 DB 규칙. 관계가 있어도 일부러 안 건 곳이 있다 | |

관계의 개수(1 : N인지 N : M인지)는 **현실에서 몇 개까지 생길 수 있는지**로 정했다. "보통 하나"가 아니라 "둘 이상이 될 수 있으면" N으로 둔다.

### 3-2. 관계마다 이유

| 부모 → 자식 | 관계 | 왜 이 개수인가 | FK |
|---|---|---|---|
| `store` → `store_override` | 1 : N | 가게 하나에서 상호·QR결제·업종처럼 **여러 필드**를 따로 고칠 수 있다. 필드마다 고친 사람·사유가 다르다. 한 필드는 한 행(PK = 가게 + 필드) | 있음 |
| `store` → `store_snapshot` | 1 : N | 가게 하나가 **버전마다** 한 행씩 있다(이번 버전, 직전 버전). PK = 버전 + 가게 | **없음**(3-4절) |
| `data_version` → `store_snapshot` | 1 : N | 버전 하나에 가게 21만 곳 | **없음**(3-4절) |
| `data_version` → `refresh_job` | 1 : N | 같은 날 두 번 돌리거나 실패한 작업이 있을 수 있다. 실패 작업은 버전이 없을 수도 있어서 빈칸 허용 | 있음 |
| `data_version` → `store`(마지막 확인 버전) | 1 : N | 가게마다 원천에서 마지막으로 본 버전 하나. 몇 주 빠졌는지 계산에 쓴다 | 있음 |
| `member` → `member_auth` | 1 : N | 한 사람이 **카카오와 구글을 둘 다** 연결할 수 있다. 회원 표에 칸으로 두면 제공자가 늘 때마다 칸을 늘려야 한다 | 있음, 탈퇴 정리 때 함께 삭제 |
| `member` → `member_recent_search` | 1 : N | 회원당 최근 검색어 10개 | 있음, 함께 삭제 |
| `member` ↔ `store` (`member_favorite`) | **N : M** | 회원 한 명이 여러 가게를, 가게 하나가 여러 회원에게 즐겨찾기될 수 있다. 그래서 가운데 연결 표가 필요하고, PK = 회원 + 가게라 같은 가게를 두 번 넣지 못한다 | 둘 다 있음 |
| `admin_user` → 수정·갱신·숨김 기록 | 1 : N | 관리자 한 명이 여러 가게를 고치고 여러 갱신을 돌린다. 숨김 처리자(`visibility_changed_by`)는 한 번도 숨긴 적 없으면 빈칸이라 선택적 관계 | 있음 |
| `search_log` ↔ `event_log` | 1 : N(논리) | 검색 하나에서 클릭·길찾기 같은 행동이 여러 번. `query_id`로 이어 본다 | **없음**(3-4절) |

### 3-3. 1 : 1을 두지 않은 이유

- 첫 설계(v0.1)에는 `store`(상태) : `store_source`(원천 값)가 1 : 1이었다. 가게 하나에 원천 행도 하나라 **나눌 이유가 없어서** v0.3에서 한 표로 합쳤다. 조인이 줄고 갱신이 단순해진다.
- 약관도 `terms` + `member_terms_agreement`(N : M)였지만, 약관 묶음은 한 번에 동의하므로 **회원 행에 동의한 묶음 버전과 시각**만 둔다.

### 3-4. 관계가 있어도 FK를 일부러 안 건 곳

| 곳 | FK를 걸면 생기는 문제 | 대신 |
|---|---|---|
| `store_snapshot` → `store`, `data_version` | 새 파티션을 붙일 때 DB가 21만 행을 다시 검사해서 **전환이 느려진다** | 전환 전에 "없는 가게 번호 0건" 검사 쿼리를 돌린다 |
| `search_log`, `event_log` → 가게·세션·검색 | 쓰기가 매번 부모 표를 확인해 느려지고, 월별 파티션 삭제가 꼬인다. 폐업 가게를 가리키는 옛 로그도 남아야 한다 | 통계 계산 때 없는 값은 버린다 |

ERDCloud 그림에는 관계가 보이도록 스냅샷의 두 선(→ `store`, → `data_version`)을 그려 두었다. 실제 DB(`schema.sql`)에는 없다.

### 3-5. 가게–업종, 가게–결제는 N : M인데 왜 연결 표가 없나

- 가게 하나가 업종 여러 개·결제 수단 여러 개를 가질 수 있어 원래는 N : M이다.
- 검색은 범위(1km·10km·지역)로 먼저 거른 뒤 남은 수백~수천 곳에서 칩을 확인한다. 이때는 스냅샷 행 안의 **목록 칸**(`category_codes`, `payment_codes`)을 보는 편이 연결 표를 조인하는 것보다 단순하고 빠르다.
- 업종·결제 코드표(`category`, `payment_method`)는 그대로 두고, 갱신 작업이 코드표에 있는 값만 넣는다.

## 4. 일부러 정규화에서 벗어난 곳

정규화(같은 정보를 한 곳에만 두기)가 기본이지만, 검색 속도와 단순함을 위해 아래는 일부러 어겼다. 자세한 대응은 `DB_DESIGN.md` 2-3절.

| 곳 | 이유 |
|---|---|
| 스냅샷이 상호·주소를 다시 가짐 | 검색마다 원천 + 수정 값을 합치는 계산을 할 수 없다. 버전별로 고정된 값이어야 한다 |
| 업종·결제를 목록 칸으로 | 3-5절 |
| `search_log.results`(목록) | 2-5절 |
| `brand_alias`에 대표 이름 반복 | 브랜드가 수십 개라 반복이 작고 표 하나로 관리가 쉽다 |

## 5. 키를 이렇게 정한 이유

| 키 | 선택 | 이유 |
|---|---|---|
| 가게 `store_id` | UUID(기존 번호 유지) | 평가 정답이 이 번호로 연결. 새 가게만 새로 발급 |
| 회원·로그 | UUID | 순번이 드러나지 않고, 화면과 서버가 따로 만들어도 겹치지 않는다 |
| 관리자·작업·별칭 | 자동 증가 번호 | 내부에서만 쓴다 |
| 업종·결제·제외어·확장어 | 코드나 정규화한 글자 자체 | 사람이 읽을 수 있고 중복이 자연히 막힌다 |
| 여러 칸 PK | `store_override`(가게 + 필드), `store_snapshot`(버전 + 가게), `member_favorite`(회원 + 가게), `member_recent_search`(회원 + 검색어), 로그(번호 + 시각) | "이 조합은 하나뿐"이 업무 규칙이라 그대로 PK로. 로그는 월별 파티션이라 시각이 PK에 들어가야 한다 |

## 6. 첫 설계(v0.1, 36개)와 달라진 점

ERDCloud에 예전에 그렸던 그림(37개)은 v0.1이다. v0.3에서 19개로 줄였다(2026-11-13 "필수 테이블만" 결정).

| v0.1에 있던 표 | 지금 | 줄인 이유 |
|---|---|---|
| `store_source` | `store`에 합침 | 1 : 1이라 나눌 이유 없음(3-3절) |
| `source_file`, `refresh_staging_row` | `refresh_job`의 파일 정보 칸, 갱신 작업 메모리 | 파일 하나 = 작업 하나. 중간 행은 작업이 끝나면 필요 없다 |
| `store_edit_history`, `store_status_history`, `store_override_alert` | 마지막 수정 정보, `status_changed_at`, `source_changed` 표시 | 이력은 남기지 않기로(2-4절) |
| `admin_access_log` | 없음 | 남기지 않기로 결정(법무 답에 따라 다시 볼 수 있음) |
| `search_result_log`, `stats_daily_query`, `event_dedup` | `search_log.results`, 로그에서 바로 계산, 통계 때 중복 제거 | 로그를 검색 로그 하나 중심으로(2-5절) |
| `terms`, `member_terms_agreement` | `member`의 약관 버전·동의 시각 | 3-3절 |
| `member_refresh_token` | 세션 저장소(Redis) | 로그인 유지 토큰은 짧게 살고 자주 바뀌어 DB보다 세션 저장소가 맞다 |
| `brand_alias_group`, `gazetteer_version`, `gazetteer_entry`, `branch_suffix`, `reference_revision` | 한 표씩으로 합침, 검색 서버가 계산, 표마다 `updated_at` | 데이터가 작고 관리 화면도 1차에는 없다(2-6절) |

## 7. 포기한 것과 다시 필요해지면

| 포기한 것 | 다시 필요해지면 |
|---|---|
| 수정·상태·숨김 이력 | 이력 표를 추가하고, 수정·상태 변경 때 한 행씩 쓴다. 지금 표는 그대로 |
| 관리자 접속 기록 | 법무에서 필요하다고 하면 로그 표 하나 추가 |
| 이전 버전으로 되돌리기 | 직전 버전 파티션이 남아 있어 구조상 가능하지만 기능은 만들지 않는다 |
| 벡터 근사 색인(HNSW) | 실제 DB에서 넓은 지역 검색이 느리면 그때 만든다(`DB_DESIGN.md` 5-3절) |
