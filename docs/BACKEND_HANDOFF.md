(Kohavi et al., *Trustworthy Online Controlled Experiments*, 2020). 단 로그는 처음부터 넣는다(Google *Rules of ML* — 지표·로그 먼저).

## 1-1. 옮길 때 그대로 지켜야 하는 동작(평가 결과가 이 동작에 맞춰져 있음)

| 동작 | 이유 |
|---|---|
| **문자 BM25로만 들어온 후보(상호 일치가 아닌 것)는 v1 점수 0(정규화 최솟값)** — 메모리 임베딩이 있다고 모든 후보에 실제 코사인을 붙이지 않는다 | 모든 후보에 실제 코사인을 붙이면 dev 10km 목록 nDCG 0.828 → 0.804, 상위 3개 실패 3.7% → 5.6%(11-21). 실제 코사인은 상호·브랜드 쿼리의 상호 일치 후보에만(`real_cosine: name`) |
| v1 점수는 **그 단계 후보 안 min-max** 정규화(1위 = 1) | 코사인 절대값은 쿼리마다 크기가 달라('원단'·'서점' 같은 짧은 쿼리는 정답도 낮음) 절대값을 쓰면 관련 확률이 무너진다(11-26). 대가로 업종 쿼리의 1위는 늘 P ≈ 0.505 → 1km에 맞는 가게가 없어도 1위 하나는 보인다(알려진 동작) |
| 임베딩 쿼리는 **쿼리 전체**(지명 포함), 문자 BM25 쿼리는 지명·서술어·지점 접미사를 뺀 단어 | 임베딩에서 지명을 빼면 dev 10km nDCG −0.012, 좁은 지역 −0.060(시장·지점 이름이 업종 신호를 담음 — 11-27) |
| 관련 확률 특성은 **그 단계 후보 집합 안**에서(1km 단계 = 1km 후보로 1단계를 다시 계산) | 계수가 그렇게 학습됨. 10km·지도 후보로 다시 학습해도 나아지지 않았다(11-24) |
| **'맨 위 가게'(브랜드 지점·상호 완전 일치, 점수 ≥ 50)가 목록에 하나라도 있으면 나머지는 P ≥ 0.7만**(`brand_others_min_p`) — 의도(intent)가 아니라 목록 기준. 맨 위 가게는 관련 확률 특성 계산에서 뺀다 | 평가한 동작이 이것. 범위 안 지점이 없는 브랜드 쿼리는 0.35 그대로(BHC 지점이 없는 곳에서 BYC가 보일 수 있음 — 개선 후보) |
| 상호 완전 일치는 검색 중심 50km 안만 | 점수 = 100 − 거리가 50 아래로 내려가면 일반 후보로 섞여 관련 확률이 무너진다 |
| 지점 접미사 목록(`branch_suffixes`, 현재 5,239개)은 파일로 내보내 쓴다 | 다시 계산하면 가맹점 갱신마다 달라진다 — 갱신 때 함께 재생성 |
| 확장 목록 순서 = 브랜드 지점·상호 완전 일치(둘 다 점수 100 − 거리라 함께 거리순) → 1km 안 P ≥ 0.5 → 나머지(1km 약한 가게 + 10km) 유사도순 | 팀 결정(1km 먼저) + P0 + 11-22 |
| 모든 거리 규칙(반경, 같은 지명 30km, 상호 우선 10km, 브랜드 거리순, 상호 완전 일치 50km)의 기준점은 **검색 중심**(정책 `location.priority` — 지도 포커스). GPS 좌표를 따로 넣지 않는다 | 10-30 회의 결정. 평가 좌표도 검색 중심 하나였다(`understanding.parse(center_lat, center_lon)`) |
| 문자 BM25(1단계·확장 모두)는 **전국(좌표 유효 21만 곳) 색인 하나**, char 2–3gram, k1 1.5, b 0.75, 음수 idf는 0(`expansion.SparseBM25`). 앱 메모리에서 계산하고 `pg_trgm`·`ts_rank`로 대신하지 않는다 | 평가의 1단계 run은 판정 반경 안 가게로 IDF를 계산했지만, 전국 IDF로 다시 만들어도 dev 1km·10km·지역·지도 모든 지표가 같았다(차이 0, 11-29). 식이 달라지면 `bm25_rel` 특성이 계수와 어긋난다 |
| 동점 규칙 없음 — '점수 차 0.01 이내면 가까운 순'은 넣지 않는다 | 평가하지 않은 규칙. 체인 지점은 브랜드 거리순이 처리 |
| 확장어 캐시 키 = **정규화한 전체 검색어**(지명 포함): NFKC → 앞뒤 공백 제거 → 연속 공백 하나로 → 영문 소문자. 캐시에 없으면 확장 없이 검색 | 평가에서 확장어는 쿼리 문장 전체로 만들었고, 10km·지역 요청 756개 모두 검색어가 캐시 쿼리와 같았다 |

## 1-4. 알려진 한계(화면·운영에서 대응)

- **DB에 없는 가게 이름 검색**(세종 서주헤어 등): 비슷한 업종 가게를 대신 보여 준다 → 상호 쿼리인데 상호 일치가 없으면 "정확히 일치하는 가게는 없어요" 안내를 추천.
- 품목이 '음식'·'한식'뿐인 가게가 많아 상황형 쿼리(복날 음식, 도시락)가 약하다 — 데이터 보강(공식 업종 등)이 오면 다시 본다.
- 동음·글자 겹침('시계 배터리' → 자동차 배터리, '하루 묵을 곳' → 상호 '하루').
- 쿼리 이해: 가맹점에서만 나온 작은 지명(가게 5곳 미만)을 버릴 때 그 단어의 다른 해석(시장 이름 부분 일치 등)을 다시 찾지 않는다 — 드문 경우, 개선 후보.
- 쿼리 이해가 '오케이 정형외과'를 지명 '오케이' + 업종으로 읽는다(코퍼스 유래 짧은 지명 키) — 지명 사전 정리 후보.

## 3. 이 저장소의 상태

지표 실험은 끝났다(X1 → X5 → X2+X3 → X7 → X8 → P0 → P2 → 최종 test 1회, `docs/SERVICE_PIPELINE_PLAN.md` 11-4 ~ 11-29).
test는 이 구성으로 이미 썼으므로, 이후 개선은 새 판정(또는 서비스 로그)으로 다시 검증해야 한다.
