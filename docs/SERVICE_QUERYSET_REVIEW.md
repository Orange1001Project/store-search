## 1. C에서 업종·품목명형 쿼리를 A로 분리

### 문제

C는 상황 카드에서 출발한 쿼리이고, 작성 안내는 업종 이름이 떠오르면 그대로 써도 된다고 했다(`docs/QUERY_WRITING_GUIDE.md`).
그래서 C 181개 중 절반 넘게 "쌀", "치과", "동네 미용실"처럼 업종·품목 이름을 그대로 쓴 쿼리다. 이 쿼리들은 점수가 A와 같고,
상황형 C와는 크게 다르다. 섞여 있으면 C 점수가 "추론이 필요한 검색"을 재지 못한다.

| 구분 | 쿼리 수 | 평균 nDCG@10 | 실패율(0.5 미만) |
|---|---|---|---|
| 기존 A | 219 | 0.821 | 6% |
| C 중 A로 옮길 쿼리 | 101 | 0.847 | 4% |
| C 중 남길 상황형 | 69 | 0.591 | 38% |

주 평가셋 test의 C 16개 중 상황형은 4개뿐이다. 지금 보고하는 C 점수는 사실상 업종·품목 쿼리 점수다.

### 기준

작성할 때가 아니라 **다 쓴 뒤 분류할 때** 적용한다. 작성자는 지금처럼 카드만 보고 쓴다.

| 규칙 | 조건 | 예 |
|---|---|---|
| A1 | 가게 종류 이름이 있다 | 치과, 동네 미용실, 쌀집, 이불 빨래방 |
| A2 | 파는 물건·서비스 이름이 있다(대상·모양 수식어는 붙어도 된다) | 우산, 쌀 사는 곳, 캠핑 장비 파는 곳, 학생 체육복, 예쁜 그릇 |
| A3 | 수리·수선의 대상이 가게 데이터에 업종처럼 적혀 있다 | 휴대폰 수리, 구두 수선, 바지 길이 수선 |
| C1 | 상황·목적·행사·증상 단어가 있다 | 집들이 선물, 제사용 술, 이유식 재료, 감기 걸리면 가는 병원 |
| C2 | 수리·수선의 대상이 가게 데이터에 없다 | 운동화 수선, 수도꼭지 수리 |
| C3 | 어떤 가게인지 하나로 떠오르지 않는다 | 따뜻한 국물, 늦은 밤 식사할 곳, 길거리 간식 |

- 판단 질문은 "이 쿼리를 보고 가게 종류를 하나로 바로 말할 수 있나"다. 말할 수 있으면 A, 여러 종류가 가능하면 C다.
  예: "우산" → 정답이 우산·양산 가게 한 종류, "자취용품" → 잡화·주방용품·생활용품·식료품·슈퍼로 퍼진다.
- 상황 단어와 물건이 함께 있으면 C로 둔다(과일 선물세트, 하객 원피스).
- A·C 속성(단체 예약, 심야, 맛집)은 지금처럼 `attribute`로 따로 집계한다.

**A3·C2의 근거**: 가게 데이터에는 업종 칸이 없고 상호와 취급품목뿐인데, 수리·수선 가게는 취급품목에 업종처럼 적혀 있다.

| 단어 | 취급품목에 이 단어가 있는 가게 | 자주 나오는 값 |
|---|---|---|
| 수선 | 544 | 옷수선 160, 수선 116, 의류수선 106, 구두수선 6 |
| 수리 | 544 | 자동차수리 108, 오토바이수리 12, 가전제품수리 12, 컴퓨터수리 9, 휴대폰수리 8 |

"운동화 + 수리·수선"인 가게는 0곳, "노트북수리"는 2곳이다.

### 결과

| | 쿼리 수 |
|---|---|
| A로 옮김 | 103 (A1 36, A2 55, A3 12) |
| C에 남김 | 73 (C1 54, C2 4, C3 15) |
| 검토 필요(`needs_review=Y`) | 13 — 하객룩, 눈 검사할 곳, 시린이 치약, 바비큐 등 |

분류는 위 규칙으로 제안한 초안이다. 같은 표현이 다른 묶음에 있던 경우(컴퓨터 수리 A / 컴퓨터 수리점 C, 옷 수선하는 곳 A /
옷 수리점 C)도 이 분류로 같은 쪽이 된다.

### 반영 방법 (정할 것)

지금 코드는 묶음 변경을 막는다. `changes_from_previous`는 기존 쿼리의 묶음이 바뀌면 가져오기를 멈추고, query_id에 묶음이
들어 있어(`sq_C123`) 묶음을 바꾸면 새 ID가 붙어 판정과 끊긴다.

| 방법 | 바꿀 곳 | 장점 | 단점 |
|---|---|---|---|
| (1) 평가용 묶음 칸 추가(제안) | `queries.csv`에 `eval_bundle` 칸, 주 평가셋(`service_eval.py`, `build_service_eval_set.py`)·채점(`score_service_eval.py`)이 이 칸을 쓴다 | query_id·판정·split 그대로 | 칸이 하나 는다 |
| (2) 묶음 자체 변경 | 설정에 이동 목록, 가져오기 검사·ID 규칙·split 고정 키(`bundle|basis`) 수정 | 묶음이 깔끔하다 | 고칠 곳이 많고 위험하다 |

어느 쪽이든 같이 바뀌는 것:

- **판정 규칙**: 옮긴 쿼리는 C 규칙("보통 사람이 그 말로 찾을 가게")으로 판정됐다. A 규칙으로 정답이 바뀔 만한 쿼리(예: "쌀" 정답이 편의점)는 다시 볼지 정한다.
- **주 평가셋**: 전체 쿼리에서 C는 26% → 11%로 줄고 test 46개(1km 정답 있음)가 남는다. 주 평가셋 비율(설정값)에서 C를 5%로
  유지하면 주 평가셋 크기는 그대로(2절)이고, C 16개가 모두 상황형이 된다.
  C를 15% 이상으로 올리면 C가 가장 모자란 묶음이 되어 주 평가셋 전체가 줄어든다(15%면 test 약 306, 20%면 약 230).
- **A head/tail**: 옮긴 쿼리는 tail로 들어가 A 구성이 바뀐다.
- **문서**: `docs/SERVICE_QUERYSET.md`(묶음 정의), `docs/QUERY_WRITING_GUIDE.md`(분류는 작성 뒤에 한다는 점).

## 2. 묶음별 개수와 보충할 양

v1과 Arctic의 쿼리별 점수 차이가 흔들리는 정도(sd)로, 차이를 구분하는 데 필요한 test 수를 계산했다(유의수준 5%, 검정력 80%).
C를 1절대로 나눈 뒤 기준이다.

| 묶음 | test(1km 정답 있음) | sd | Δ0.05에 필요 | Δ0.03에 필요 | 판단 |
|---|---|---|---|---|---|
| A | 230 | 0.152 | 73 | 202 | 충분 |
| B | 160 | 0.170 | 91 | 253 | Δ0.05까지 충분 |
| C | 46 | 0.215 | 146 | 404 | 주 평가셋엔 충분, C만 따로 결론 내기엔 부족 |
| D | 38 | 0.180 | 102 | 283 | 부족(큰 실패 확인용이면 그대로) |
| E | 23 | — | — | — | 정답이 없어 nDCG로 못 잰다 |

"비율"은 두 가지다. 헷갈리지 않게 나눠 쓴다.

| | 뜻 | C를 A로 옮기면 |
|---|---|---|
| 전체 쿼리 구성비 | 판정된 쿼리 690개가 묶음별로 몇 개인지(센 값) | 바뀐다: A 33% → 48%, C 26% → 11% |
| 주 평가셋 비율(설정값) | `eval_set.shares`의 B50 / A35 / D10 / C5. 채점용 주 평가셋을 이 비율로 뽑는다 | 그대로다(설정값이라 바꾸지 않는 한 같다) |

**주 평가셋 크기는 그대로다.** 주 평가셋은 묶음마다 "쓸 수 있는 쿼리 수 ÷ 주 평가셋 비율"이 가장 작은 묶음이 크기를 정한다.
지금처럼 B가 정해(test 160 ÷ 0.5 = 320) test 320 / dev 108 그대로이고, C는 16개만 있으면 된다(남는 상황형 C는 46개).
그래서 **주 평가셋 비율에서 C 5%는 유지하고, 주 평가셋을 위한 보충은 하지 않는다.**

- **C(선택)**: C 묶음만 따로 결론(예: "상황 검색은 모델 X가 낫다")을 내려면 test 약 100개가 더 필요하다. dev 25%, 1km 정답 없음,
  중복을 감안하면 새로 약 150개다. 보충하지 않으면 C는 큰 실패를 확인하는 용도로 쓴다. 지금 46개로도 Δ0.10(필요 약 36개)은
  구분된다(v1과 Arctic의 C 차이는 0.10).
- **D(선택)**: Δ0.05까지 보려면 새로 약 90개.
- **B**: 3절에서 빠지는 만큼만 채운다.

### C를 보충한다면

- `scenario_cards_extra`에 새 카드를 더하고 `scripts/make_writer_sheets.py`로 작성 시트를 만든다. 완료본은 `import.writers_completed`에 더한다. 코드 수정은 없다.
- 카드는 지금처럼 업종·품목 이름 없이 쓴다. 종류를 고르게: 선물·행사, 명절·계절, 문제 해결, 생활 사건(이사·자취·출산), 목적·모임.
- 쓰는 사람은 업종 목록·가게 데이터를 보지 않은 사람이 좋다. 쓴 뒤 1절 기준으로 분류하면 일부는 A로 간다.

## 3. B 상호 쿼리 기준

B는 표본 가게·체인에서 거꾸로 쓴 쿼리라 어느 가게를 찾는지는 정해져 있다. 문제는 결과가 사용자에게 다른 뜻으로 읽힐 때다.

| 규칙 | 내용 | 예 |
|---|---|---|
| B1 | 상호 일부만 쓸 때는 업종 꼬리만 뗀다. 고유 부분만 남기면 ① 그 단어로 가게가 떠오르고 ② 사람 이름·지역명·일반 단어가 아니며 ③ 다른 뜻으로 읽히지 않아야 한다 | 유지: 아이콘 안경, 교촌 / 검토: 효준, 청송, 이지, GS |
| B2 | 상호가 업종명·음식명이면 B에서 뺀다(지역 있으면 D, 없으면 A). 표본으로 받으면 건너뛴다 | 부산 신평시장 손칼국수, 냉삼맛집 |
| B3 | 상호가 유명한 장소·시설 이름과 같으면 업종·지점을 붙이거나 뺀다 | 강촌 엘리시안, 만남의 광장 |
| B4 | 공식 표기(한글·영문)는 허용, 철자 오기는 오타 정책을 따른다 | 허용: 씨유, 비비큐 / 회의: 파리바게트, 베스킨라빈스 |

B1 판단에 쓸 수 있는 데이터 신호(상호·주소에 그 단어가 들어간 가게 수):

| 단어 | 상호 | 주소·시장명 | 해석 |
|---|---|---|---|
| 교촌 | 162 | 34 | 같은 체인 — 유지 |
| 이지 | 277 | 235 | 서로 다른 가게가 많음 — 일반 단어 |
| 손칼국수 | 170 | 28 | 서로 다른 가게가 많음 — 업종명 |
| 청송 | 98 | 116 | 주소에 더 많음 — 지역명 |
| 효준 | 2 | 1 | 데이터로는 판단 불가 — 사람이 본다 |

- 고유 부분만 남긴 11개 중 9개를 W1, 2개를 W3이 썼다. 작성 안내에 B1을 더한다.
- B에 `b_type`(브랜드 / 브랜드+지점 / 상호 전체 / 상호 일부 / 지역+상호)을 두고 주 평가셋에서 A head/tail처럼 비율을 정한다.
  상호 전체 쿼리 43개는 실패가 0개라 모델 차이를 거의 보여주지 못한다.
- 데이터 정리: '송도 올룸' 의도 칸 빈칸, '현대자동차 보성점' 의도 칸 오타('현대자동자').
- 처리 대상 19개(모두 주 평가셋, test 17 / dev 2)는 CSV `area=B`.

## 4. 보고와 test 수정 원칙

- 전체 점수와 묶음별 점수(A head / A tail / B / C / D)를 항상 같이 적는다. 주 평가셋 비율(설정값 B50/A35/D10/C5)은 우리 서비스
  검색 로그 없이 정한 가정이라고 적는다. 근거로 든 Broder(2002)·Silverstein(1999)는 일반 웹 검색 로그 연구라(`docs/SERVICE_PIPELINE_PLAN.md`
  7절), 묶음별 숫자 자체는 팀이 그 경향을 보고 정한 값이다. 근거 페이지(노션 "평가·학습 쿼리 구성 기준 검토")와 숫자를 정한 과정을 함께 확인한다.
- test는 stage 1에서 이미 채점했다. 쿼리를 옮기거나 빼는 것은 점수가 아니라 이 문서의 규칙으로만 하고, 쿼리마다 이유를 남긴다.
  고치기 전 결과는 따로 보관한다. 문자열이 바뀌는 쿼리는 새 query_id로 다시 판정한다.
