## 1. C에서 업종·품목명형 쿼리를 A로 분리

### 문제

C는 상황 카드에서 출발한 쿼리이고, 작성 안내는 업종 이름이 떠오르면 그대로 써도 된다고 했다(`docs/QUERY_WRITING_GUIDE.md`).
그래서 C 181개 중 절반 넘게 "쌀", "치과", "동네 미용실"처럼 업종·품목 이름을 그대로 쓴 쿼리다. 이 쿼리들은 점수가 A와 같고,
상황형 C와는 크게 다르다. 섞여 있으면 C 점수가 "추론이 필요한 검색"을 재지 못한다.

| 구분 | 쿼리 수 | 평균 nDCG@10 | 실패율(0.5 미만) |
|---|---|---|---|
| 기존 A | 219 | 0.821 | 6% |
| C 중 A로 옮길 쿼리 | 107 | 0.838 | 6% |
| C 중 남길 상황형 | 63 | 0.582 | 38% |

주 평가셋 test의 C 16개 중 상황형은 4개뿐이다. 지금 보고하는 C 점수는 사실상 업종·품목 쿼리 점수다.

### 기준

작성할 때가 아니라 **다 쓴 뒤 분류할 때** 적용한다. 작성자는 지금처럼 카드만 보고 쓴다.

판단 질문은 하나다: **"이 쿼리를 보고 가게 종류를 하나로 바로 말할 수 있나?"** 말할 수 있으면 A, 여러 종류가 가능하면 C다.
판정된 정답 가게가 한 종류로 모이는지로 확인한다. 상황 단어(하객, 선물)가 있어도 정답이 한 종류로 모이면 A다.

| 규칙 | 조건 | 예 |
|---|---|---|
| A1 | 가게 종류 이름이 있거나, 가게 종류가 하나로 정해진다 | 치과, 동네 미용실, 쌀집, 이불 빨래방, 눈 검사할 곳(안경점) |
| A2 | 파는 물건·서비스 이름이 있다(대상·모양·상황 수식어는 붙어도 된다) | 우산, 쌀 사는 곳, 학생 체육복, 하객 원피스, 과일 선물세트 |
| A3 | 수리·수선의 대상이 가게 데이터에 업종처럼 적혀 있다 | 휴대폰 수리, 구두 수선, 바지 길이 수선 |
| C1 | 상황·목적·행사·증상만 있고 정답이 여러 종류 가게로 퍼진다 | 집들이 선물, 제사용 술, 이유식 재료, 자취용품 |
| C2 | 수리·수선의 대상이 가게 데이터에 없다 | 운동화 수선, 수도꼭지 수리 |
| C3 | 어떤 가게인지 하나로 떠오르지 않는다 | 따뜻한 국물, 야식, 술안주 파는 곳 |

- 예: "우산" → 정답이 우산·양산 가게 한 종류, "하객룩" → 옷가게 26곳으로 한 종류, "자취용품" → 잡화·주방용품·생활용품·식료품·슈퍼로 퍼진다.
- A·C 속성(단체 예약, 심야, 맛집)은 지금처럼 `attribute`로 따로 집계한다.

**A3·C2의 근거**: 가게 데이터에는 업종 칸이 없고 상호와 취급품목뿐인데, 수리·수선 가게는 취급품목에 업종처럼 적혀 있다.

| 단어 | 취급품목에 이 단어가 있는 가게 | 자주 나오는 값 |
|---|---|---|
| 수선 | 544 | 옷수선 160, 수선 116, 의류수선 106, 구두수선 6 |
| 수리 | 544 | 자동차수리 108, 오토바이수리 12, 가전제품수리 12, 컴퓨터수리 9, 휴대폰수리 8 |

"운동화 + 수리·수선"인 가게는 0곳, "노트북수리"는 2곳이다.

### 결과

| | 쿼리 수 |
|---|---|
| A로 옮김 | 109 (A1 37, A2 60, A3 12) |
| C에 남김 | 67 (C1 48, C2 4, C3 15) |

애매했던 13개는 검토해서 정했다(2026-10-28): 하객룩·하객 원피스·눈 검사할 곳·시린이 치약·과일 선물세트·이력서 사진·
자전거 바람 넣는 곳·카네이션 화분·노트북 고장 수리·단체 회식 고깃집 → A, 술안주 파는 곳·야식·바비큐 → C. 13개 모두 주 평가셋 밖이다.
같은 표현이 다른 묶음에 있던 경우(컴퓨터 수리 A / 컴퓨터 수리점 C, 옷 수선하는 곳 A / 옷 수리점 C)도 이 분류로 같은 쪽이 된다.

### 반영 방법 — 평가용 묶음 칸

묶음 자체는 바꾸지 않는다. 지금 코드는 묶음 변경을 막고(`changes_from_previous`), query_id에 묶음이 들어 있어(`sq_C123`)
묶음을 바꾸면 새 ID가 붙어 판정과 끊긴다. 대신 **평가할 때 쓰는 묶음**만 바꾼다.

- 목록: `data/query/service_eval_bundle_v1.csv`(109줄 — query_id, query, bundle, eval_bundle, rule)
- 설정: `eval_set.bundle_overrides`(`configs/query/service_queryset_v1.yaml`)
- 코드: `service_eval.apply_eval_bundle` — 사례의 `bundle`을 평가용 묶음으로 바꾸고 원래 묶음은 `source_bundle`에 남긴다.
  목록의 bundle이 지금 묶음과 다르거나, 없는 query_id·모르는 묶음·중복이 있으면 멈춘다.
  `build_service_eval_set.py`, `score_service_eval.py`(per_instance에 `source_bundle` 열 추가), `eval_service_pipeline.py`가 쓴다.
- 바뀌지 않는 것: query_id, 판정(qrels), split, 사례, pool·판정 시트의 묶음(판정 규칙).
- 확인: `build_service_eval_set.py --dry-run` — test 320(B160 / A112 / D32 / C16), dev 108로 크기 그대로. 이전 셋 대비 14개가
  바뀐다(업종·품목명형 C 14개가 A로 세어져 A 14개가 빠지고, C 자리는 상황형 14개로 채워짐). 테스트 `tests/test_service_eval.py`.

같이 정할 것:

- **판정 규칙 — 재판정하지 않는다(팀 결정, 2026-10-29)**: 옮긴 쿼리는 C 규칙("보통 사람이 그 말로 찾을 가게")으로 판정됐고 그대로 쓴다.
  두 규칙은 대부분 같은 답을 주고 차이는 "쌀 → 편의점" 같은 경계 사례뿐이며, 주 평가셋에 든 옮긴 쿼리는 14개다. 보고에
  "A 중 C에서 옮긴 109개는 C 규칙으로 판정"이라고 적고, 필요하면 `source_bundle`로 따로 본다.
- **주 평가셋 비율(설정값)에서 C**: 전체 쿼리에서 C는 26% → 10%로 줄고 test 42개(1km 정답 있음)가 남는다. C 5%를 유지하면 크기는
  그대로이고(2절) C 16개가 모두 상황형이 된다. C를 15% 이상으로 올리면 C가 가장 모자란 묶음이 되어 주 평가셋 전체가 줄어든다
  (15%면 test 약 280, 20%면 약 210).
- **A head/tail**: 옮긴 쿼리는 tail로 들어가 A 구성이 바뀐다.
- **결과 다시 만들기**: 합의 뒤 `build_service_eval_set.py` → `score_service_eval.py` → `eval_service_pipeline.py` 순서. 바꾸기 전 결과는 따로 보관한다(4절).
- **문서**: `docs/SERVICE_QUERYSET.md`(묶음 정의), `docs/QUERY_WRITING_GUIDE.md`(분류는 작성 뒤에 한다는 점).

## 2. 묶음별 개수와 보충할 양

v1과 Arctic의 쿼리별 점수 차이가 흔들리는 정도(sd)로, 차이를 구분하는 데 필요한 test 수를 계산했다(유의수준 5%, 검정력 80%).
C를 1절대로 나눈 뒤 기준이다.

| 묶음 | test(1km 정답 있음) | sd | Δ0.05에 필요 | Δ0.03에 필요 | 판단 |
|---|---|---|---|---|---|
| A | 234 | 0.158 | 79 | 219 | 충분 |
| B | 160 | 0.170 | 91 | 252 | Δ0.05까지 충분 |
| C | 42 | 0.198 | 124 | 344 | 주 평가셋엔 충분, C만 따로 결론 내기엔 부족 |
| D | 38 | 0.180 | 103 | 284 | 부족(큰 실패 확인용이면 그대로) |
| E | 23 | — | — | — | 정답이 없어 nDCG로 못 잰다 |

"비율"은 두 가지다. 헷갈리지 않게 나눠 쓴다.

| | 뜻 | C를 A로 옮기면 |
|---|---|---|
| 전체 쿼리 구성비 | 판정된 쿼리 690개가 묶음별로 몇 개인지(센 값) | 바뀐다: A 33% → 49%, C 26% → 10% |
| 주 평가셋 비율(설정값) | `eval_set.shares`의 B50 / A35 / D10 / C5. 채점용 주 평가셋을 이 비율로 뽑는다 | 그대로다(설정값이라 바꾸지 않는 한 같다) |

**주 평가셋 크기는 그대로다.** 주 평가셋은 묶음마다 "쓸 수 있는 쿼리 수 ÷ 주 평가셋 비율"이 가장 작은 묶음이 크기를 정한다.
지금처럼 B가 정해(test 160 ÷ 0.5 = 320) test 320 / dev 108 그대로이고, C는 16개만 있으면 된다(남는 상황형 C는 42개).
그래서 **주 평가셋 비율에서 C 5%는 유지하고, 주 평가셋을 위한 보충은 하지 않는다.**

- **C — 보충하지 않는다(팀 결정, 2026-10-29)**: C는 큰 실패를 확인하는 용도로 쓴다. C 묶음만 따로 결론(Δ0.05)을 내려면 test가
  약 80개(새로 약 120개) 더 필요하다는 점은 보고에 적는다. 지금 42개로도 Δ0.10(필요 약 31개)은 구분된다(v1과 Arctic의 C 차이는 0.10).
- **D(선택)**: Δ0.05까지 보려면 새로 약 90개.
- **B**: 보충하지 않는다(3절 — 빼는 쿼리가 없다).

### 나중에 C를 보충한다면

- `scenario_cards_extra`에 새 카드를 더하고 `scripts/make_writer_sheets.py`로 작성 시트를 만든다. 완료본은 `import.writers_completed`에 더한다. 코드 수정은 없다.
- 카드는 지금처럼 업종·품목 이름 없이 쓴다. 종류를 고르게: 선물·행사, 명절·계절, 문제 해결, 생활 사건(이사·자취·출산), 목적·모임.
- 쓰는 사람은 업종 목록·가게 데이터를 보지 않은 사람이 좋다. 쓴 뒤 1절 기준으로 분류하면 일부는 A로 간다.

## 3. B 상호 쿼리 — 빼지 않고 유지

B는 표본 가게·체인에서 거꾸로 쓴 쿼리라 어느 가게를 찾는지는 정해져 있다. 처음에는 상호 일부만 쓴 쿼리("효준", "청송"),
상호가 업종명인 쿼리("부산 신평시장 손칼국수")를 빼자고 봤다. 하지만 **가게를 아는 사람이 실제로 칠 수 있는 검색어**이고, 이 셋은
가정 위치 근처에서 검색하므로 근처에서 찾는 가게가 하나로 정해지는지가 기준이다. 근처 1km로 보면 대부분 하나로 정해진다.

| 쿼리 | 찾는 가게 | 1km 안에 이 단어가 상호에 든 가게 | v1 nDCG@10 |
|---|---|---|---|
| 청송 | 청송반찬 | 1 (청송반찬) | 0.96 |
| 이지 | 이지+ | 1 | 0.88 |
| 경민 / 이근철 / 재해석 | 경민상회 / 이근철청과 / 재해석 | 각 1 | 0.70 / 0.73 / 0.73 |
| 광원 | 광원세라믹 | 1 | **0.00** |
| 제이엘 / 바운드 / 공백 | 제이엘 필라테스 / 바운드본점 / 공백커피 | 각 1 | 1.00 / 1.00 / 0.83 |
| 효준 | 효준횟집 | 2 (효준수산, 효준횟집) | 0.55 |
| GS | 주변 GS25 | 3 (모두 GS25) | 1.00 |
| 성남 속풀이 해장국 / 영산포 닭갈비마을 | 속풀이 해장국 / 닭갈비 마을 | 각 1 | 0.80 / 0.90 |
| 냉삼맛집 | 여기는 냉삼맛집 | 2 | 0.90 |
| 강촌 엘리시안 / 월곡시장 만남의 광장 | 엘리시안 강촌 렌탈샵 / 만남의 광장 | 각 1 | 1.00 / 0.94 |
| 부산 신평시장 손칼국수 | 손칼국수 | **3** (고향손칼국수, 정가네칼국수, 손칼국수) | 1.00 |

전국 기준(예: 상호에 '청송'이 든 가게 98곳, '이지' 277곳)으로는 애매해 보이지만, 판정·채점은 반경 안에서만 하므로 근처 기준으로 본다.

### 기준

| 규칙 | 내용 |
|---|---|
| B1 | 상호 일부, 지역+상호, 상호가 업종명인 쿼리도 **유지**한다. 근처(1km)에서 찾는 가게가 하나로 정해지면 그대로 쓴다 |
| B2 | 근처에 같은 업종 가게가 여럿이라 "그 업종 아무 데나"로도 읽히면 판정을 확인한다. 지금 B 규칙은 같은 업종 다른 가게가 1점인데, 2점으로 볼지 정한다(해당: 부산 신평시장 손칼국수) |
| B3 | `b_type`(브랜드 / 브랜드+지점 / 상호 전체 / 상호 일부 / 지역+상호)을 표시해 묶음 안에서 따로 집계한다 |

- **빼거나 고치지 않으므로 B 수(test 160)와 주 평가셋 크기(test 320)는 그대로다. B 보충도 필요 없다.**
- 빼면 모델이 실제로 실패하는 사례를 숨긴다. 예: "광원"은 v1이 0점이다.
- 상호 전체 쿼리 43개는 실패가 0개라 모델 차이를 거의 보여주지 못한다. 상호 일부 쿼리가 오히려 차이를 보여준다.
  상호 전체를 따로 보고 싶으면 기존 쿼리를 바꾸지 말고 추가 쿼리로 더한다(예: '효준'은 두고 '효준횟집'을 더함).
- 철자 차이(파리바게트, 베스킨라빈스 등)는 이 검토에서 다루지 않는다(팀 결정) — 그대로 유지한다.
- 데이터 정리: '송도 올룸' 의도 칸 빈칸, '현대자동차 보성점' 의도 칸 오타('현대자동자').
- 위 19개의 제안은 CSV `area=B`.

## 4. 보고와 test 수정 원칙

- 전체 점수와 묶음별 점수(A head / A tail / B / C / D)를 항상 같이 적는다. 주 평가셋 비율(설정값 B50/A35/D10/C5)은 우리 서비스
  검색 로그 없이 정한 가정이라고 적는다. 근거로 든 Broder(2002)·Silverstein(1999)는 일반 웹 검색 로그 연구라(`docs/SERVICE_PIPELINE_PLAN.md`
  7절), 묶음별 숫자 자체는 팀이 그 경향을 보고 정한 값이다. 근거 페이지(노션 "평가·학습 쿼리 구성 기준 검토")와 숫자를 정한 과정을 함께 확인한다.
- test는 stage 1에서 이미 채점했다. 쿼리를 옮기거나 빼는 것은 점수가 아니라 이 문서의 규칙으로만 하고, 쿼리마다 이유를 남긴다.
  고치기 전 결과는 따로 보관한다. 문자열이 바뀌는 쿼리는 새 query_id로 다시 판정한다.
