## 3. 데이터가 흐르는 길

| 흐름 | 순서 |
|---|---|
| **검색** | 화면 → ② 검색어 해석(메모리) → ③에 검색어 벡터 요청(150ms 넘거나 실패하면 글자 검색만, FR-FBK) → ④에서 범위 안 가게와 벡터 비교 + ②의 BM25 → ② 점수·관련 확률·정렬 → 결과 300곳을 ② 메모리에 10분 보관, 첫 20곳 응답 → 검색 로그 한 행(비동기) |
| **다음 페이지** | ② 메모리의 결과에서 21~40위. 10분 지났거나 서버가 재시작됐으면 410 → 화면이 같은 조건으로 다시 검색 |
| **주간 갱신** | 운영자가 서버에서 ②의 갱신 명령 실행(엑셀 경로 + 관리자 계정) → 검사 → 같은 가게 판단(사업자번호 + 가맹점명 + 도로명 주소) → 바뀐 가게만 ③으로 벡터 → ④에 새 버전 파티션 → 그사이 관리자 수정·숨김 다시 적용 → 한 트랜잭션으로 전환 → ②가 새 버전으로 BM25·사전을 다시 올림 |
| **관리자 수정** | 화면 A-04 → ② → `store_override` 저장 → 활성 사본의 그 가게 행 갱신(상호·품목이면 ③으로 벡터도) → 1분 안 검색 반영 |
| **DB 직접 작업(1차)** | 별칭·지명 제외·좌표·관리자 계정은 운영자가 ④에 직접 → ②가 1분마다 바뀐 표를 다시 읽음 |
| **로그인(P1)** | 화면 → ② → 카카오·구글 → ② 회원 확인·가입 → 접근·갱신 토큰 쿠키(갱신 토큰은 ④ `member_refresh_token`에 해시) |
| **정기 작업** | ② 스케줄러: 매일 새벽 일별 통계·만료 토큰 삭제, 매달 두 달 앞 로그 파티션 생성, 1년 지난 로그·갱신 작업 삭제 |

## 4. AI가 들어가는 곳

| 것 | 형태 | 언제 쓰나 | 어디서 |
|---|---|---|---|
| 임베딩 모델(bge-m3 미세조정 v1, fp32) | 모델 폴더 `bge_m3_ft_mj_20261014_0743`(수 GB, git 밖·Drive) | 검색마다 검색어 1개, 갱신 때 바뀐 가게만 | ③ |
| 정책 값 | `configs/service/search_policy_v1.yaml` | ② 시작 때 읽고 검사(틀리면 시작 실패, FR-RNK-08) | ② 메모리 |
| 관련 확률 계수 | `results/service_pipeline/x1/calibrator.json` | 같음 | ② 메모리 |
| LLM 확장어 | 미리 만든 결과(Qwen2.5-14B) → `expansion_cache` 표 | 업종 검색 때 조회만 | ④ → ② 메모리 |
| 업종 체계 | `configs/category/taxonomy_v1.yaml`, `ksic_onnuri_v1.csv` | 갱신 때 | ② |

- **가게 벡터와 검색어 벡터는 같은 모델**이어야 한다. 데이터 버전마다 쓴 모델을 남기고(`data_version.embedding_model`), 모델을 바꾸면 전체 벡터를 다시 만들어 새 버전으로 전환한다.
- LLM은 1차에 돌리지 않는다(주간 생성은 P2).
- 검색 로직은 파이썬 평가 코드가 기준이다. 평가 질의별 "정답 결과 파일"을 뽑아 자바 결과와 비교한다(NFR-QLT-01).

## 6. 왜 이렇게 정했나 — 구성 요소별

설계 기준은 세 가지다. **PoC라서 단순하게, 평가한 검색 결과는 그대로, 키울 때 갈아엎지 않게.**

### 6-1. 서버 1대 + Docker Compose

- PoC라 사용자가 적다. 서버가 여러 대면 네트워크·방화벽·백업을 대수만큼 챙겨야 한다.
- Docker Compose는 "이 프로그램들을 이 설정으로 같이 띄운다"를 파일 하나로 적는다. 로컬과 서버가 같은 파일을 써서 "내 PC에선 되는데 서버에선 안 돼요"가 줄어든다(예: PostGIS 버전 차이).
- 대가: 서버가 멈추면 전체가 멈추고, 배포 때 API 서버가 몇 초 재시작된다. PoC에서는 받아들인다(8절).

### 6-2. Nginx

| 이유 | 없으면 |
|---|---|
| HTTPS 인증서를 한 곳에서 관리(무료 인증서 자동 갱신) | Spring이 인증서를 직접 다루고, 인증서를 바꿀 때마다 API 서버를 재시작 |
| 화면 파일은 바뀌지 않는 파일이라 전달 전용 서버가 빠르고 가볍다 | API 서버가 화면 파일 전달에 자원을 씀 |
| 화면과 API를 **같은 주소**(`example.com`, `example.com/api`)로 묶는다 | 주소가 다르면 쿠키 로그인·CSRF 설정이 까다로워짐(교차 출처) |
| API 서버를 늘리면 요청을 나눠 준다 | 앞단을 새로 만들어야 함 |

### 6-3. Spring Boot, 그리고 검색 로직을 자바로

- 팀 백엔드가 Java·Spring이다(정책 17-1). 회원·보안·스케줄러·JPA가 기본으로 있다.
- **검색 해석·점수 계산도 자바로 옮긴다**(정책 4-10). 임베딩 서버가 멈춰도 해석과 글자 검색은 돌아야 하기 때문이다. 해석이 파이썬 서버에 있으면 그 서버가 멈출 때 검색이 통째로 멈춘다.
- BM25 색인과 사전을 **메모리**에 둔다. 검색마다 DB에서 사전을 읽으면 느리다.
- BM25를 DB 글자 검색(`pg_trgm`, `ts_rank`)으로 하지 않는다. 점수 식이 평가 때 식과 달라 관련 확률 계수가 맞지 않게 된다(인계 문서 동작 9).
- 주간 갱신·정기 작업도 **같은 코드의 명령**으로 둔다. 같은 가게 판단·벡터 생성 코드를 두 곳에 두지 않으려고.

### 6-4. 임베딩 서버를 따로 둔 이유

| 이유 | 예 |
|---|---|
| 모델이 파이썬(PyTorch, sentence-transformers)으로 학습됐다. 자바로 옮기면 벡터가 미세하게 달라질 위험 | 소수점 차이로 순위가 바뀔 수 있음 |
| 메모리를 많이 쓰고 무겁다. API 서버와 **같이 죽지 않게** | 모델이 멈춰도 API 서버는 글자 검색으로 버팀(폴백) |
| 나중에 GPU로 옮기거나 대수를 늘리기 쉽다 | 임베딩 서버만 GPU 서버로 |
| 갱신 때도 같은 서버를 쓴다 | 검색어와 가게가 반드시 같은 모델 |

### 6-5. DB 하나(PostgreSQL + PostGIS + pgvector)

| 이유 | 다른 방법을 안 쓴 까닭 |
|---|---|
| 위치·벡터·일반 데이터를 한 DB에서 | 벡터 전용 DB를 따로 두면 "1km 안 + 벡터 비교"를 두 시스템에서 나눠 하고 동기화가 생긴다 |
| "범위 안 가게 중 벡터가 가까운 순"을 SQL 한 번으로 | 범위로 먼저 좁히면 보통 수백 곳이라 정확히 계산해도 빠르다(근사 색인 없음) |
| 버전 전환을 트랜잭션 한 번으로 | 여러 시스템이면 반은 새 버전·반은 옛 버전 상태가 생길 수 있다 |
| 회원·로그도 같은 곳에서 | 팀이 익숙한 SQL·JPA |

버전별 검색 사본(파티션)과 월별 로그 파티션은 22만 곳을 매주 갈아끼우고 로그를 1년 뒤 통째로 지우기 위한 것이다. 행을 하나씩 지우는 것보다 칸째 떼는 것이 빠르다. 자세한 이유는 [`db/DB_DESIGN_WHY.md`](db/DB_DESIGN_WHY.md).

### 6-6. Redis를 쓰지 않는 이유(PoC)

Redis가 맡을 일은 두 가지였다. 서버가 1대라 둘 다 다른 곳에서 할 수 있다(2026-11-16 결정).

| 일 | PoC에서 | 잃는 것 |
|---|---|---|
| 검색 결과 300곳 10분 보관 | API 서버 메모리 캐시(10분 뒤 자동 삭제) | 서버 재시작 때 보던 목록이 만료 → 화면이 자동 재검색(이미 정한 동작) |
| 로그인 갱신 토큰(14일) | DB 표 `member_refresh_token`(해시만) | 없음. 배포·재시작해도 로그인 유지, 로그아웃·탈취 감지도 그대로 |

구성 요소가 하나 줄어 설치·감시·백업할 것이 줄어든다. 코드에서 캐시와 토큰 저장을 인터페이스로 감싸 두면, 서버를 늘릴 때 그 부분만 Redis로 바꾼다.

### 6-7. 그 밖의 선택

| 선택 | 이유 |
|---|---|
| React | 지도 위 3단계 하단 시트처럼 상태가 많은 화면에 맞고 팀이 익숙하다 |
| 네이버 지도 | 국내 주소·길찾기 정확도, 사용자 폰의 네이버 지도 앱으로 길찾기를 바로 넘김 |
| GitHub Actions | 코드가 이미 GitHub에 있어 배포 도구를 따로 두지 않는다 |
| Flyway | 팀원 PC와 서버의 DB 구조를 같은 순서로 맞춘다 |
| 갱신은 화면 대신 명령 | 주 1회 일이라 화면 비용보다 명령이 싸다(화면은 P2) |
| LLM은 1차에 안 돌림 | 상시 GPU가 비싸고, 미리 만든 확장어로 평가 수치가 이미 나왔다 |
| 모델 파일은 git·이미지 밖 | 수 GB라 저장소·이미지가 무거워진다. 폴더 이름이 곧 버전 |

## 7. PoC에서 단순화한 것

| 요구사항 | PoC | 정식 서비스 |
|---|---|---|
| 무중단 배포(NFR-OPS-06) | 배포 때 API 서버가 몇 초 재시작(데이터 버전 전환은 무중단, NFR-OPS-02) | API 서버 2대 + Nginx 분산으로 번갈아 배포 |
| 환경 분리(개발·검증·운영) | 로컬 + 서버 1대(검증 겸 운영) | 검증·운영 서버 분리 |
| 가용성 99.5%(NFR-OPS-01) | 서버 1대라 장애 때 전체 중단 | DB 별도·이중화 |
| 백업·시점 복구(NFR-OPS-05) | 매일 DB 덤프 보관 | 관리형 DB의 시점 복구 |

## 8. 나중에 바뀔 수 있는 곳
