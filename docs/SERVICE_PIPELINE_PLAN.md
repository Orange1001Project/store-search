서비스셋(`docs/SERVICE_EVAL_METHOD.md`)으로 검색 파이프라인을 서비스 목표까지 끌어올리는 순서다. 원칙은 단계별로 개발·평가하고

**합성 학습 데이터는 넣지 않았다**(이전 결정, 2026-10-19). 2-2는 기존 train 쿼리로만 하므로 학습 쿼리 수(215개)가 한계다.
2-2로도 목표에 못 미치면 학습 쿼리를 늘리는 방법(사람이 더 쓰기 등)을 그때 정한다.

## 2. 왜 이 순서인가

- **1단계를 먼저 하는 이유**: 하이브리드와 reranker는 모델을 다시 학습하지 않고도 바로 효과를 볼 수 있다. 실패 분석상 B는 어휘 매칭이,
  C는 재정렬이 처방이다. 업계에서도 "1단계 검색(BM25+임베딩) → 2단계 재정렬"이 기본 구조다.
- **임베딩 재학습을 뒤로 둔 이유**: reranker가 있으면 1단계 임베딩에 필요한 것은 "상위 k 안에 정답을 넣는 것"(재현율)으로 바뀐다.
  재학습 목표를 1단계 결과를 보고 정해야 헛수고가 없다.
- **기능(3단계)을 뒤로 둔 이유**: 근처에 없음 처리·위치·분류는 순위 품질이 갖춰진 다음에 그 위에 얹는 처리다.
  특히 3-1의 임계값은 reranker 점수 분포에 따라 달라지므로 reranker를 정한 뒤에 한다.

## 3. 평가 규칙(이 계획 전체에 적용)

- 모든 구성은 **반경 안에서** 평가한다(1km 주 지표, 2km 보조). 판정은 기존 qrels를 그대로 쓴다.
- dev로 고르고 test는 단계 끝에 한 번. dev 사례는 139개(1km, A 41 / B 39 / C 46 / D 13) — 설정 몇 개를 고르는 데 쓰고,
  차이가 0.02 미만이면 단순한 쪽을 고른다.
- 새 구성의 상위 10개에 판정 안 된 가게가 많으면(Judged@10 < 0.95) 점수가 낮게 나온다 → 1-4 보충 판정 뒤에 비교한다.
  dev 비교 단계에서는 판정된 문서만 남긴 nDCG@10(condensed)을 같이 본다.

## 4. 벡터 DB — 이 단계(3-4)에서 정하되, 1단계 결과로 요구사항이 정해진다

### 4-1. 우리 규모와 검색 방식에서 필요한 것
- 문서 21만 개 × 1024차원 float32 ≈ 0.9GB. 벡터 DB가 필요한 규모(수천만~수억)보다 훨씬 작다.
- 서비스는 **현재 위치 1km 안**만 본다. 반경 안 후보는 중앙값 약 300곳, 상위 10%도 1,200곳 정도다.
  → **지리 필터로 후보를 먼저 줄이고 그 안에서 벡터 점수를 전부 계산(exact)** 하면 ANN 근사 오차가 없고 속도도 충분하다.
  ANN(HNSW 등)은 전국 검색이나 반경을 크게 늘릴 때만 필요하다.
- 1단계 실험 결과로 정해질 요구사항: 하이브리드(BM25+벡터 결합)를 엔진 안에서 해야 하는지, 한국어 형태소 BM25가 필요한지,
  reranker를 붙일지(엔진 밖 서빙).

### 4-3. 권장 (잠정)
- **1순위 OpenSearch**: 한국어 형태소 BM25(nori), 벡터 검색, 반경 필터, 하이브리드 결합을 한 엔진에서 할 수 있고 Apache 2.0이다.
  1-1·1-2가 "하이브리드가 필요하다"로 나오면 가장 자연스럽다.
- **2순위 PostgreSQL + pgvector + PostGIS**: 가맹점 데이터가 이미 PostgreSQL에 있고 운영 인력이 RDB 중심이면 유리하다.
  반경 필터 후 exact 계산이라 ANN 성능 걱정이 없다. 한국어 BM25는 확장(PGroonga 등)이나 별도 엔진이 필요하다.
- 어느 쪽이든 3-4에서 **지금 실험 결과와 같은 순위가 나오는지**(반경 필터 + exact면 거의 같아야 함), p95 지연, 가맹점 추가·변경
  반영 주기, 장애 시 BM25 단독 폴백을 확인한다.

### 1-1 하이브리드 (2026-10-23, dev 1km 139 사례) — **채택: v1 + 상호 일치 가산점(β=0.5)**

- **RRF는 열세**: BM25가 v1보다 크게 약한 묶음(A·C)에서 순위만 보는 RRF가 BM25 오답을 같은 무게로 끌어올린다. Bruch et al.(2023)의
  "튜닝된 가중합 > RRF"와 같은 결과. (k가 커질수록 판정 안 된 문서가 늘어 Judged@10도 0.90까지 떨어짐.)
- **일괄 가중합은 묶음끼리 맞바꿈**: α=0.7은 B를 올리지만(0.869→0.916) C를 깎는다(0.736→0.708). 상황형 쿼리에서 BM25는 해롭다.
- **상호 일치 가산점**(지역 표현을 뺀 쿼리와 상호가 서로 포함, 3글자 이상 → 정규화 점수 +β, `fusion.name_match`/`boost`):
  BM25 후보까지 합친 목록에서 이름이 맞는 가게만 끌어올리므로 B는 가중합만큼 오르고 C는 그대로다. 신호는 B 180 사례 중 139에서,
  그 밖에는 17 사례(상호에 업종명이 든 맞는 가게, 예: ○○태권도장)에서만 켜졌다. β=0.3~1.0 차이는 0.004 이내 → 가운데 값 0.5.
  가중합을 더해도(α=0.9+이름) 차이가 없어 **단순한 쪽(v1+이름)을 채택**.
- 전체 nDCG 이득은 +0.014(3절의 0.02 기준 미만)지만 목표로 한 B에서 +0.042, B 1위 정답률 0.872→0.974라 채택한다. 규칙 하나라 비용이 없다.
- **남은 문제**: bad@3 0.144(목표 0.05), C bad@3 0.348 — 하이브리드로는 C가 안 움직인다. 다음은 1-3 reranker.
  1-2(형태소 BM25)는 BM25가 B 외에는 도움이 안 되고 B는 상호 일치로 해결돼 **보류**(reranker 뒤에 B가 다시 문제면 재검토).
