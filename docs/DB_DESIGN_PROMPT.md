너는 실무 경험이 풍부한 백엔드 개발자이자 데이터베이스 설계자야.
아래 문서를 바탕으로 실제 개발에 쓸 관계형 데이터베이스(ERD·테이블)를 설계해줘.
내가 설계를 이해하고 팀원에게 설명할 수 있도록 선택한 이유와 주의점도 쉽게 설명해줘.
나는 검색 품질 평가(판정) 담당이라 DB 용어에 익숙하지 않아. 용어는 처음 나올 때 풀어서 설명하고, 가능하면 아래 실제 데이터 예시로 보여줘.

> 갱신 2026-11-11 · 기준: 요구사항 정의서 v0.3 이후(`docs/REQUIREMENTS.md`)
> 이 프롬프트는 요구사항을 다시 적지 않는다. **요구사항 정의서가 기준이고, 이 프롬프트와 다르면 요구사항 정의서를 따른다.**

## 3. 바꾸면 안 되는 제약

- `store_id`는 이미 발급된 UUID를 그대로 쓴다(평가 정답 데이터가 이 ID로 연결). 새 가게만 새로 발급.
- 같은 가게 판단(지문) = 사업자번호 + 가맹점명 + 주소, **원천 값**으로 계산. 상호·주소가 바뀌면 새 가게.
- 원천 파일은 고치지 않고, 가맹점 행은 지우지 않는다(상태로 관리).
- 검색 점수·노출·정렬, BM25는 애플리케이션 메모리에서 계산한다(DB 전문 검색 함수 금지). DB는 범위 안 후보 조회와 벡터 유사도, 원문 제공을 맡는다.
- PostgreSQL 16 + PostGIS 3.4 + pgvector 0.8 이상, Spring Boot + JPA. 벡터 전용 DB 없음.
- 저장은 UTC, 하루·한 달·데이터 버전 날짜는 **한국 시간** 기준(파티션 경계 포함).
- 분석 로그에 회원 ID를 넣지 않는다. 최근 검색어에 좌표·query_id를 넣지 않는다. 위치는 100m 격자만 저장한다.

## 4. 설계에서 특히 답해야 할 것

요구사항 정의서를 읽고 아래는 반드시 설계로 답을 보여줘.

1. **데이터 버전(FR-UPD-06·07)**: 주간 갱신은 새 버전을 다 만든 뒤 한 번에 전환하고, 검색 한 건은 한 버전만 본다. 벡터(DR-04)뿐 아니라 **가게 정보·상태·업종·지점 접미사도 버전마다** 달라진다. 무중단 전환이 되는 구조(버전 열, 스테이징 테이블, 스냅샷 등)를 고르고 이유를 설명해줘. 가장 중요한 부분이다.
2. **원천 값과 관리자 수정 값(DR-01·02, FR-STO)**: 필드별 수정·해제, 수정 우선 적용, 원천이 바뀌면 알림, 갱신 도중 들어온 수정을 전환 직전 새 버전에 다시 적용(FR-UPD-07).
3. **가게 상태(P10-5·10-6)**: 영업중 / 확인 대기 / 폐업, 관리자 숨김, 좌표 오류. "2주 연속 없음"을 셀 수 있는 구조와 상태 이력(DR-03). 검색 대상 = 영업중이고 숨김·좌표 오류가 아닌 가게.
4. **결제 수단 확장**: 지금은 카드·QR(원천 모바일) 두 가지, 바코드는 데이터가 오면 추가된다. 열을 늘리지 않고 붙일 수 있는 구조인지 판단해줘. 결제 칩 필터(FR-MSG-04) 조회도 고려.
5. **로그(DR-16·17)**: 검색·노출·이벤트를 한국 시간 월 단위 파티션으로, 1년 지나면 파티션째 삭제. 외래 키를 걸지 여부(쓰기 성능·파티션 삭제·폐업 가게 참조)와 `event_id` 중복 제거 방법. 일별 통계 테이블 단위.
6. **회원(DR-13·14·19)**: 회원–로그인 수단 1:N, 닉네임 중복 허용, 이메일·닉네임 선택, 약관 동의 기록, 탈퇴 즉시 삭제, 최근 검색어 10개 유지·즐겨찾기 500곳 제한을 동시 요청에서도 지키는 방법.
7. **관리자(DR-15)**: 권한 한 단계, 비밀번호 해시·잠금, 접속 기록(보관 기간은 설정값).
8. **참조 데이터(DR-07~12)**: 업종, 브랜드 별칭, 지명 사전, 지명 제외 목록, 지점 접미사, 확장어 캐시. 서버가 메모리에 올려 쓰므로 "버전 바뀜"을 알 수 있는 방법(최대 1분 반영).

## 5. 정해지지 않은 것 (가정하고 진행, 가정은 표로 명시)

| 항목 | 상태 | 진행 방법 |
|---|---|---|
| 원천 모바일결제가 QR결제만 뜻하는지 | 데이터 제공 부서 확인 전 | 컬럼은 원천 뜻 그대로(모바일)로 두고, 화면 이름 매핑은 설정으로 |
| 중복 행끼리 결제 값이 다를 때 | 규칙 없음 | 하나라도 Y면 Y로 가정하고 충돌 표시 |
| 지명만 입력('신촌')을 최근 검색어에 남기는지 | 미정 | 남기는 것으로 가정(구조 영향 없음) |
| 문구 ⑥ 기준 0.52, 위치 정밀도, 보관 기간, 안전장치 % | 확인 중 | 모두 설정값(테이블 구조는 그대로) |

질문이 꼭 필요하면 최대 5개만, 선택지와 추천 이유를 붙여서 먼저 물어봐줘. 요구사항에 없는 기능은 추가하지 마.

## 6. 결과 순서

1. **요구사항 정리**: 저장할 데이터, 생성·수정·삭제 흐름, 상태 전이, 확정·가정 구분
2. **테이블 구성과 관계**: 테이블별 역할, 1:1·1:N·N:M과 연결 테이블, **Mermaid ERD**, 각 테이블이 어느 DR·FR에서 왔는지 표
3. **테이블 상세 명세**: 테이블마다 표(컬럼명, 자료형·길이, PK/FK·참조, NULL, 기본값, UNIQUE·CHECK, 설명). snake_case 통일. 자료형·길이·식별자 선택 이유(특히 `vector(1024)`, `geography` vs `geometry`, 로그 ID UUID vs bigint, 문자열 번호, JSONB vs 컬럼)
4. **무결성과 변경 정책**: 중복·잘못된 참조 방지, 부모 삭제·상태 변화 때 자식 처리, 물리·논리 삭제, 이력 보존, 동시 요청(즐겨찾기 두 번 클릭, 최근 검색어 10개 초과, 즐겨찾기 500 초과, 갱신 두 번 동시 실행, 갱신 중 관리자 수정, 이벤트 재전송)
5. **주요 조회와 인덱스**: 아래 조회 SQL과 필요한 인덱스, 복합 인덱스 순서 이유, 불필요한 인덱스 검토
   - 검색 중심 1km/10km 원 안 + 벡터 유사도 상위 50(현재 데이터 버전, 검색 대상만, 업종·결제 칩 필터는 점수 뒤라 SQL 밖)
   - 법정동 코드 앞 2·5·8자리 + 벡터 유사도 상위 50
   - 지도 화면 사각형 안 가게(최대 300)
   - 검색어 없는 조회(화면 안 가게, 업종·결제 칩)
   - 회원 최근 검색어·즐겨찾기 목록, 관리자 가맹점 조회(FR-STO-01), 관리자 통계(일별 요약)
   - 벡터 색인(HNSW)이 지금 필요한지: 범위로 먼저 거르고 전부 계산하는 방식이라 필요 없을 수 있다. 10km·넓은 지역(시도 전체)에서 후보가 커지는 경우까지 따져서 판단
6. **테이블 생성 SQL**: CREATE EXTENSION / CREATE TABLE, PK·FK·UNIQUE·CHECK·인덱스, 외래 키 순서, 로그 월별 파티션 생성·삭제 예시(한국 시간 경계)
7. **설계 검토**: 중복·갱신 이상, 요구사항 중 반영 못 한 것(DR·FR ID로), 과하게 쪼갠 테이블, 팀이 더 정할 것

정규화를 기본으로 하되, 분리·반정규화는 조회 패턴을 근거로 판단해줘. 여러 안이 가능하면 추천안 하나를 중심으로 쓰고 중요한 대안만 장단점을 비교해줘.
