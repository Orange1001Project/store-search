너는 실무 경험이 풍부한 백엔드 개발자이자 데이터베이스 설계자야.
아래 프로젝트 요구사항을 바탕으로 실제 개발에 사용할 관계형 데이터베이스의 테이블을 설계해줘.
내가 설계를 이해하고 팀원에게 설명할 수 있도록, 선택한 이유와 주의점도 쉽게 설명해줘.
나는 검색 품질 평가(판정) 담당이라 DB 용어에 익숙하지 않아. 용어는 처음 나올 때 풀어서 설명하고, 가능하면 아래 실제 데이터 예시로 보여줘.

(기준: 검색 정책 v1 — 저장소 PR #9 `configs/service/search_policy_v1.yaml`, `docs/BACKEND_HANDOFF.md`, `docs/SEARCH_LOGGING.md`,
그리고 2026-11-10 팀 결정. 아래 "확정"은 다시 묻지 말고 그대로 반영해줘.)

## 프로젝트 정보

### 서비스 소개
- 전국 전통시장·골목형상점가 가맹점 **214,043곳**을 자연어로 찾는 지도 기반 가게 검색 서비스.
  예: "통닭", "고기 파는 곳", "머리 자르는 곳", "신촌 설렁탕", "GS25", "피양옥".
- 검색 방식: 가게마다 `가맹점명: {상호} / 취급품목: {품목}` 문장을 임베딩 모델(bge-m3 미세조정, 1024차원 벡터)로 벡터화해 두고
  검색어 벡터와의 유사도로 순위를 매기는 의미 검색 + 글자 단위 키워드 점수(BM25)를 함께 쓴다.

### 주요 사용자와 역할 (확정)
- **비회원**: 검색·지도·가게 상세는 로그인 없이 가능.
- **회원**: **소셜 로그인만**(카카오·네이버 등, 휴대폰 본인인증 없음). 받는 정보는 **로그인 제공자 + 제공자 고유 ID뿐**
  (이메일·닉네임·실명 없음). 나중에 다른 로그인 수단(예: 디지털온누리 계정 연동)을 붙일 수 있게 **회원과 로그인 수단을 분리**한다.
  회원 전용 기능은 ① 최근 검색어 ② 가게 즐겨찾기.
- **관리자**: 일반 회원과 별도 계정, **권한은 한 단계**(모든 관리자가 같은 권한). 하는 일:
  ① 가맹점 정보 수정·숨김 ② 주간 가맹점 갱신 실행·결과 확인 ③ 검색 로그·통계 조회.
  권한은 하나지만 **누가 무엇을 했는지는 모두 기록**한다(아래 관리자 접속 기록).

### 주요 기능과 업무 흐름

**1. 검색** (검색 품질 실험으로 확정된 동작. DB는 이 흐름에 필요한 데이터를 담아야 한다)

| 단계 | 하는 일 | DB에 필요한 것 |
|---|---|---|
| 검색 중심 | 우선순위: 검색어 속 지명 > 화면에서 고른 지역(지역 메뉴·"다른 신촌" 선택) > 지도를 옮긴 현재 화면 중심 > GPS > 기본 위치(소상공인시장진흥공단 본부, 대전 유성구 지족로364번길 92). **모든 거리 규칙의 기준점은 검색 중심**이고 GPS는 검색 중심을 정할 때만 쓴다 | 지명 사전 |
| 검색어 해석 | 지명을 떼고 남은 말을 상호 / 브랜드 / 업종으로 분류(규칙). 예: "신촌 설렁탕" → 지역 신촌 + 업종 | 지명 사전, 브랜드 별칭 |
| 검색 범위 | 지명 없음 → 중심 1km(부족하면 10km). 넓은 지명(시도·시군구·읍면) → **법정동 코드 앞자리**로 거름. 좁은 지명(동·역·시장) → 그 중심 1km(→10km). 지도 모드 → **화면 사각형** 안 | 가게 좌표, 법정동 코드 |
| 후보 모으기 | 범위 안에서 임베딩 상위 50 ∪ 글자 BM25 상위 50. 업종 검색어는 미리 만든 **LLM 확장어**로 BM25 상위 200 추가 | 가게 벡터, 가게 텍스트, 확장어 캐시, 지점 접미사 목록 |
| 점수 | 후보 안에서 0~1로 맞춘 유사도 + 0.5 × 상호 일치 (+ 업종 검색어는 0.3 × 확장 BM25). 거리는 점수에 넣지 않음 | |
| 맨 위 가게 | 브랜드 지점, 상호 완전 일치(검색 중심 50km 안) → 가까운 순으로 항상 맨 위 | 브랜드 별칭 |
| 보여 줄지 판단 | 관련 확률(로지스틱 식, 계수 파일) ≥ 0.35만 노출. 맨 위 가게가 있으면 나머지는 ≥ 0.7 | 정책·계수 버전 |
| 반경 확장 | 1km 관련 가게가 10개 미만이면 10km까지(상호 검색도 같은 규칙). 순서: 맨 위 가게 → 1km 안 확률 ≥ 0.5 → 나머지 점수순 | |
| 지도 모드 | 화면 사각형 안 관련 가게 전부(확장 없음), **상한 300곳**(점수순). 지도를 옮기면 '이 지역에서 다시 검색' 버튼(자동 검색 안 함) | |
| 업종 칩 | 사용자가 고른 업종(17개)으로 결과를 거름. 순위에는 안 씀 | 가게 업종 |
| 안내 문구 | 확장했음 / 일부 확장 / 10km에도 없음 / 지도 빈 화면 / **상호 정확히 일치 없음**("'서주헤어'와 정확히 일치하는 가게는 없어요") | 로그에 문구 종류 |
| 장애 시 | 임베딩 서버가 멈추면 **BM25 + 상호 일치만으로 검색**(폴백), 로그에 폴백 표시 | |

- 검색 1건의 후보는 수백~수천 곳이고, 범위 안 후보 **전부와 정확히** 유사도를 계산한다(근사 검색 색인 없이). 응답 목표 p95 300ms.
- 점수 계산(정규화·관련 확률·정렬)과 **BM25는 애플리케이션 메모리에서** 계산한다(확정). BM25는 전국 21만 곳 색인 하나
  (글자 2~3조각, k1 1.5, b 0.75)이고, PostgreSQL `pg_trgm`·`ts_rank`로 대신하지 않는다(점수가 달라져 관련 확률 계수와 어긋남).
  DB는 "범위 안 후보 + 벡터 유사도 상위 N"과 BM25 색인을 만들 원문 텍스트를 제공하면 된다.
- 임베딩 모델 실행 방식(Python 서버 vs 자바 ONNX)과 검색어 해석 규칙 이식은 백엔드 팀이 정한다. DB 설계는 어느 쪽이든 쓸 수 있게 해줘.

**2. 로그** (`docs/SEARCH_LOGGING.md` — OpenSearch UBI·Algolia Insights와 같은 구조, 확정)
- **수집**: 서버가 검색 응답을 만들 때 검색 1건 + 노출 결과를 **비동기로** 기록. 화면(웹·앱)은 사용자 행동 이벤트를 모아
  몇 초마다 묶어 전송(페이지를 떠날 때 `sendBeacon`, 앱은 끊기면 저장 후 재전송). 둘은 `query_id`(UUID)로 잇는다.
- **모든 이벤트 공통 필드**: `event_id`(UUID — 재전송 중복 제거), `client_ts`(화면 시각, 순서용), `server_ts`(서버 시각, 기준), `schema_version`.
- **검색 1건(search)**: query_id, session_id, 시각, 앱·파이프라인(정책·계수 버전)·가맹점 스냅샷(`corpus_version`) 버전, 검색어, 입력 방식, 업종 칩,
  검색 중심 출처(query_region / ui_region / map_viewport / gps / default), 목록/지도, 지도 화면 범위(100m 격자), 사용자 위치(**100m 격자 ID만**),
  검색어 해석 결과(지역·범위·의도), 반경 단계(1km / 10km / region / region+10km), 관련 가게 수, 화면 문구 종류, 폴백 여부, 확장어 캐시 적중 여부, 단계별 지연.
- **노출 결과**: 검색 1건당 상위 20개를 **20행으로 저장**(확정, JSON 묶음 아님): 가게, 순위(1부터), 거리, 점수. 페이지를 넘겨도 같은 query_id, 순위는 절대 순위.
- **사용자 행동(event)**: impression(카드 면적 50% 이상이 1초 이상 보임), click(가게·순위·거리), action(전화·길찾기·즐겨찾기·공유·결제),
  dwell(상세 체류 초), region_choice(다른 지역 선택), chip_change / research_here(새 query_id), cluster_click / pin_click(지도),
  reformulate(30초 안 재검색), abandon.
- **회원과 연결하지 않는다**(확정): 분석 로그에는 회원 ID가 없고 `session_id`만 둔다. 세션은 **30분 무활동이면 새 세션**.
- **봇 의심 표시**(확정): 로그를 지우지 않고 표시만 하고 통계에서 뺀다. 기본 규칙: 알려진 봇 User-Agent, 한 세션 1분 30회 초과 검색,
  화면 이벤트 없이 검색만 수백 건인 세션(숫자는 출시 뒤 조정 — 규칙과 기준값을 바꿀 수 있게).
- **보관**(확정): 원본 로그(검색·노출·행동) **1년**, 월별로 통째로 삭제. 삭제 전에 **일별 통계 요약**을 만들어 계속 보관.
- 관리자 통계: 인기 검색어, 결과 없음 비율, 확장 비율, 재검색 비율, 첫 클릭 순위, 클릭률, 의도별 지표, 확장어 캐시 적중률, 폴백 비율.

**3. 회원 기능** (확정)
- **최근 검색어**: 로그와 별도 테이블. 회원, 검색어, 시각만 저장(**좌표와 `query_id`는 넣지 않음** — 넣으면 가명 로그와 이어져 재식별됨).
  같은 검색어는 하나로 합치고 시각만 갱신. **회원당 최근 10개**(기간 제한 없음), 넘으면 오래된 것부터 삭제. 회원이 개별·전체 삭제 가능, 탈퇴 시 삭제.
- **즐겨찾기**: 회원–가게 추가·해제. 가게가 **폐업 확정 또는 관리자 숨김**이 되면 즐겨찾기 자동 삭제.
  "확인 대기"(아래) 중에는 지우지 않고 목록에서만 잠시 숨기며, 가게가 돌아오면 그대로 보인다.
- 회원 탈퇴: 회원·로그인 수단·최근 검색어·즐겨찾기 삭제. 분석 로그는 원래 회원과 연결되지 않으므로 그대로.

**4. 주간 가맹점 갱신** (확정)
- 매주 새 가맹점 파일(엑셀)을 받아 신규·변경·사라진 가게를 반영하고, 신규·변경 가게만 임베딩을 다시 만든다.
  함께 다시 만드는 것: 가게 업종, 지점 접미사 목록(상호 끝 "…점", 현재 5,239개), BM25 색인, **LLM 확장어 배치**
  (지난주 로그에서 캐시에 없던 업종 검색어를 많이 나온 순으로 생성).
- **사라진 가게**: 그 주에 바로 검색에서 빼고 "확인 대기". 다음 주에 다시 들어오면 자동 복구, **2주 연속 없으면 "폐업" 확정**. 행은 지우지 않는다.
- **안전장치**: 한 번에 너무 많은 가게가 사라지면(기준 %는 미정) 자동 반영을 멈추고 관리자 확인을 받는다.
- 관리자가 실행하고, 건수(신규·변경·확인 대기·복구·폐업)와 작업 단계별 상태를 본다. 같은 갱신이 동시에 두 번 돌면 안 된다.
- 결과와 로그에는 어떤 가맹점 스냅샷(`corpus_version`)으로 검색했는지 남긴다. 갱신 중에도 검색은 끊기지 않아야 한다.
- 원천의 실제 갱신 주기는 데이터 제공 부서에 문의 중. 주기가 바뀌어도 구조는 그대로여야 한다.

**5. 관리자 가맹점 수정·숨김** (확정: **관리자 수정 우선**)
- 원천 값과 관리자 수정 값을 **따로 저장**하고, 검색·화면에는 수정 값을 우선으로 쓴다. 관리자가 수정을 해제하면 원천 값으로 돌아간다.
- 다음 주 원천 값이 바뀌면(수정했던 필드의 원천이 달라지면) 관리자에게 "원천이 바뀌었어요, 수정을 유지할까요?" 알림.
- 상호·품목을 고치면 **고친 값으로 임베딩을 다시 만든다**. 같은 가게 판단(`entity_fingerprint`)은 계속 **원천 값**으로 계산한다.
- 숨김은 주간 갱신 뒤에도 유지된다. 수정 이력(누가·언제·무엇을·이전 값·새 값)을 남긴다.

**6. 관리자 접속 기록** (확정)
- 관리자 ID, 시각, 접속 IP, 한 일(조회한 화면·검색 조건, 수정한 가게, 실행한 갱신)을 별도로 기록. 우선 **1년 이상** 보관(법무 확인 결과에 맞춰 조정).

### 검색에 쓰는 참조 데이터 (확정: 정책·계수만 git, 나머지는 DB)
| 데이터 | 둘 곳 | 규모·예시 | 바뀌는 때 |
|---|---|---|---|
| 가게 업종(임시 v0) | DB | 17개 대분류(음식점·식품 마트·미용 …), 가게 5.5%는 여러 업종, 근거(품목/상호/없음). 업종 칩 필터를 SQL에서 건다 | 주간 갱신, 공식 업종 데이터가 오면 교체 |
| 브랜드 별칭 | DB | 65행: GS25 ↔ 지에스25, 파리바게뜨 ↔ 파리바게트. 관리자가 수정 | 수동 |
| 지점 접미사 | DB(스냅샷과 묶음) | 5,239개 | 주간 갱신 때 재생성 |
| LLM 확장어 캐시 | DB | 키 = **정규화한 전체 검색어(지명 포함)**: NFKC → 앞뒤 공백 제거 → 연속 공백 하나로 → 영문 소문자. 값 = 키워드 목록, 생성 LLM·시각. 캐시에 없으면 확장 없이 검색 | 주 1회 배치 |
| 지명 사전 | DB(버전 관리) | 21,859행: 이름, 종류(sido 30·city 28·sigungu 488·eupmyeon 2,779·dong 7,159·hdong 6,699·market 2,698·station 1,978), 넓은/좁은, 법정동 코드, 중심 좌표. 같은 이름 여러 곳 있음(예: 신촌 서울/창원) | 행정구역 개편, 공공데이터 갱신 |
| 정책 값·관련 확률 계수 | git 설정 파일, 버전만 DB·로그 | 정책 파일 1개 + 계수 JSON | 구성 변경마다 |

- DB에 두더라도 검색할 때마다 조회하지 않고, 서버 시작·버전 변경 시 메모리에 올려 쓴다(응답 300ms 목표).

### 사용 DBMS와 버전
- **PostgreSQL + PostGIS + pgvector**(팀 결정, 벡터 전용 DB는 쓰지 않음).
- 버전은 PostgreSQL 16, PostGIS 3.4, pgvector 0.8 이상으로 가정. 다르면 알려줄게.

### 기술 스택
- 웹 백엔드: **Spring Boot + JPA**(Hibernate).
- 벡터(`vector(1024)`)·공간(`geography`/`geometry`) 컬럼을 JPA에서 어떻게 다룰지(네이티브 쿼리 등)도 짚어줘.

### 예상 데이터 규모와 사용 패턴
- 가맹점: 약 21만 곳, 매주 수백~수천 곳 변동(정확한 수치는 모름).
- 벡터: 21만 × 1024차원 float32 ≈ 0.9GB.
- **공개 서비스**: 하루 검색 수만 건 이상을 가정. 검색 1건에 노출 결과 20행 + 행동 이벤트 여러 행 → 하루 수십만~수백만 행, 1년 보관.
- 주된 조회: 반경·지역·화면 사각형 안 가게 + 벡터 유사도(검색마다), 회원의 최근 검색어 10개, 즐겨찾기 목록,
  관리자 통계(기간별 집계 — 일별 요약 우선), 갱신 작업 상태.

### 기존 테이블 및 개발 제약사항
- 아직 DB 테이블은 없다. 지금은 parquet·csv 파일로 관리한다.
- **가게 식별자 `store_id`는 이미 발급된 UUID를 그대로 써야 한다.** 평가 정답 데이터(qrels)가 이 ID로 연결돼 있어서
  바뀌면 평가 데이터가 모두 깨진다. 새 가게만 새 UUID를 발급한다.
- 같은 가게 판단 기준은 `entity_fingerprint` = 사업자번호 + 가맹점명 + 주소(원천 값)의 해시. 값이 같으면 기존 `store_id`를 재사용한다.
- 사업자번호·가맹점번호·법정동코드는 숫자가 아닌 **문자열**.
- 취급품목 NULL은 "기타" 등으로 채우지 않는다.
- 원천 파일은 수정하지 않고, 새 데이터는 새 파일로 추가한다.
- 검색 동작(점수 계산 순서, 정규화 범위 등)은 평가로 확정된 것이라 DB 때문에 바꾸면 안 된다.

### 이번 범위 밖
- 오타·맞춤법 교정, 재정렬 모델(reranker), 실시간 LLM 호출, 가게 리뷰·평점, 업종으로 순위 올리기, "점수 차 0.01 이내 거리순" 규칙(평가에 없어 넣지 않음),
  상호 검색 시 1km에서 멈추는 예외(넣지 않음), 관리자 권한 등급, 회원 개인화.

### 아직 외부 답을 기다리는 것 (구조는 바꾸지 않고 값만 바뀌게 설계해줘)
- 개인위치정보 법무 확인(진행 중): 위치 저장 정밀도(지금 100m 격자), 로그·접속 기록 보관 기간이 바뀔 수 있다.
- 원천 데이터 실제 갱신 주기(데이터 제공 부서 문의 중).
- 대량 삭제 안전장치의 기준 %, 봇 규칙 기준값.

## 설계 진행 방식

1. 요구사항에서 데이터와 업무 규칙을 먼저 추출해줘.
2. 위 "확정"은 다시 묻지 마. 그래도 설계 결과를 크게 바꿀 수 있는 정보가 빠졌다면 핵심 질문을 최대 5개 먼저 해줘.
   질문할 때는 가능한 선택지와 추천 이유도 제시해줘. 특히 아래는 설계로 답을 보여줘.
   - 관리자 수정 값과 원천 값을 어떻게 나눠 저장하고, 주간 갱신 때 "원천이 바뀌었어요" 알림을 어떻게 만들지.
   - 주간 갱신 중에도 검색이 끊기지 않고, 한 검색이 섞인 스냅샷을 보지 않게 하는 방법(`corpus_version`).
   - 가게 상태(영업중 / 확인 대기 / 폐업 / 관리자 숨김)와 즐겨찾기 처리를 어떻게 연결할지.
   - 위치 저장 정밀도·보관 기간이 법무 결과로 바뀌어도 구조를 바꾸지 않는 방법.
3. 사소한 미정 사항은 합리적으로 가정해서 진행하고, 가정한 내용을 명시해줘. 요구사항에 없는 기능을 임의로 추가하지 마.
4. 현재 개발 범위에 맞게 설계하고, 향후 확장을 위한 선택 사항(공식 업종 교체, 다른 로그인 수단, 온라인 A/B 실험 등)은 별도로 구분해줘.

다음 순서로 결과를 작성해줘.

1. 요구사항과 업무 규칙

* 저장해야 할 주요 데이터
* 데이터 생성, 수정, 삭제 흐름(검색, 로그 이벤트, 주간 갱신, 관리자 수정·숨김, 회원 가입·탈퇴, 최근 검색어, 즐겨찾기, 확장어 배치)
* 중복 허용 여부, 필수 값, 상태 전이 등 지켜야 할 규칙
  (가게 상태 영업중 ↔ 확인 대기 → 폐업, 관리자 숨김 / 갱신 작업 상태 / 최근 검색어 10개 유지 / 즐겨찾기 중복 금지)
* 확정된 내용과 가정한 내용

2. 테이블 구성과 관계

* 필요한 테이블과 각 테이블의 역할
* 테이블 사이의 1:1, 1:N 관계와 필수 또는 선택 관계
* N:M 관계를 해소하는 연결 테이블(예: 회원–가맹점 즐겨찾기, 가맹점–업종)
* Mermaid ERD

3. 테이블 상세 명세
각 테이블을 아래 항목이 포함된 표로 작성해줘.

* 컬럼명
* 자료형과 길이
* PK / FK 여부 및 참조 대상
* NULL 허용 여부
* 기본값
* UNIQUE, CHECK 등 제약조건
* 컬럼 설명

테이블명과 컬럼명은 영문 snake_case로 통일해줘.
자료형, 문자열 길이, 식별자 생성 방식을 선택한 이유도 설명해줘.
특히 `vector(1024)`, 좌표 자료형(`geography` vs `geometry`), 로그 식별자(UUID vs bigint), 문자열 번호 컬럼,
검색어 해석 결과처럼 구조가 바뀔 수 있는 필드(JSONB vs 컬럼)의 선택 이유를 설명해줘.

4. 무결성과 데이터 변경 정책

* 중복 저장과 잘못된 참조를 막는 방법
* 부모 데이터 삭제 시 자식 데이터 처리 방식(가맹점 상태 변화 시 즐겨찾기와 로그, 회원 탈퇴 시 최근 검색어·즐겨찾기·로그인 수단)
* 물리 삭제와 논리 삭제 중 적절한 방식 및 이유
* 이력 보존이 필요한 데이터와 방식(관리자 수정 이력, 관리자 접속 기록, 주간 갱신 결과, 참조 데이터·정책 버전)
* 로그 테이블에 외래 키를 걸지 여부(쓰기 성능, 월별 파티션 삭제, 폐업 가게 참조를 고려)
* 여러 요청이 동시에 들어올 때 생길 수 있는 문제와, 트랜잭션 또는 제약조건으로 대응하는 방법
  (예: 즐겨찾기 버튼 두 번 클릭, 최근 검색어 동시 저장으로 10개 초과, 주간 갱신 중 검색, 주간 갱신 두 번 동시 실행,
  관리자 수정과 주간 갱신이 겹침, 같은 이벤트 재전송)

5. 주요 조회와 인덱스

* 핵심 기능에서 자주 실행할 조회 예시. 아래 검색 SQL은 꼭 포함해줘.
  ① 중심 반경(1km/10km) 안 가게 + 벡터 유사도 상위 50 ② 법정동 코드 앞자리 + 벡터 유사도 상위 50 ③ 지도 화면 사각형 안 가게
  (모두 검색 가능 상태인 가게만, 업종 칩이 있으면 업종 필터 포함)
* 각 조회에 필요한 인덱스와 선정 이유
* 복합 인덱스의 컬럼 순서와 이유
* 중복되거나 불필요한 인덱스가 없는지 검토
* 벡터 색인(HNSW)을 지금 만들어야 하는지: 범위로 먼저 거르고 전부 계산하는 방식이라 필요 없을 수 있음. 10km·넓은 지역(시도 전체)일 때 후보가 커지는 경우도 따져서 판단 근거를 줘.

조회 패턴이 불명확하다면 인덱스를 확정하지 말고 후보와 확인할 조건을 제시해줘.

6. 테이블 생성 SQL

* PostgreSQL 16 + PostGIS + pgvector에서 실행 가능한 CREATE EXTENSION / CREATE TABLE SQL
* PK, FK, UNIQUE, CHECK, 인덱스 반영
* 외래 키 의존성을 고려한 생성 순서
* 로그 테이블 월별 파티션 생성 예시와 1년 지난 파티션 삭제 방법

7. 설계 검토

* 데이터 중복과 갱신 이상 가능성
* 요구사항 중 설계에 반영되지 않은 부분
* 과도하게 복잡하거나 불필요하게 분리된 테이블
* 팀에서 추가로 결정해야 할 사항

정규화를 기본으로 하되, 테이블 분리나 반정규화는 실제 요구사항과 조회 패턴을 근거로 판단해줘.
(예: 가맹점과 벡터를 한 테이블에 둘지 분리할지, 원천 값과 수정 값을 같은 테이블에 둘지, 시장 정보를 별도 테이블로 뺄지,
취급품목·업종을 배열로 둘지 별도 테이블로 둘지, 통계 요약 테이블의 단위)
여러 설계가 가능하면 추천안 하나를 중심으로 설명하고, 중요한 대안과 장단점만 간단히 비교해줘.
